## [A44-1] Blob UAF fix is incomplete: sqlite3_value_blob(TEXT) returns NULL while sqlite3_value_bytes(TEXT) returns non-zero → NULL-deref in C extensions
- commit: c425580a "fix(sqlite3): use-after-free in sqlite3_value_blob" (2026-03-13)
- file: extensions/core/src/types.rs:353 (blob_ref); bindings/c/src/lib.rs:2435 (sqlite3_value_blob), :2447 (sqlite3_value_bytes)
- at-head: present
- category: ffi
- severity: medium
- confidence: high
- description: The commit correctly fixes the blob UAF (the old `to_blob()` returned a temporary `Vec` and `sqlite3_value_blob` handed out `.as_ptr()` into it, which dropped at end of the match arm — dangling pointer). The new `blob_ref()` borrows the underlying stable storage, so BLOB values are now handled correctly. However, the rewrite also DROPPED the `ValueType::Text` arm that the old `to_blob()` had (it used to coerce text to its bytes). Now `blob_ref()` returns `None` for Text, so `sqlite3_value_blob(text)` returns NULL — while `sqlite3_value_bytes(text)` still returns the text byte length via the `to_text()` path. Real SQLite returns a non-NULL pointer to the text bytes from `sqlite3_value_blob` on a text value. So the fix is incomplete: it fixed one crash (UAF on blobs) but leaves a NULL/length inconsistency on the text path.
- failure: A C extension registered via `sqlite3_create_function` receives a TEXT argument and reads it uniformly as bytes — the standard idiom `const void* b = sqlite3_value_blob(v); int n = sqlite3_value_bytes(v); memcpy(dst, b, n);`. With a text argument, `b == NULL` but `n > 0`, so the `memcpy` dereferences NULL with a non-zero length → segfault. In real SQLite this copies the text bytes. (Pre-fix, the same path was a UAF; the fix converts UAF → NULL-deref instead of preserving the text coercion.)
- evidence: |
    bindings/c/src/lib.rs:2435 sqlite3_value_blob -> `match v.blob_ref() { Some(b)=>..., None=>null() }`.
    extensions/core/src/types.rs:353 `pub fn blob_ref(&self) -> Option<&[u8]>` matches only `ValueType::Blob => ...`, all else `_ => None` (Text falls through to None).
    bindings/c/src/lib.rs:2447 sqlite3_value_bytes: `ValueType::Text => v.to_text().map(|s| s.len()).unwrap_or(0)` → returns text length for TEXT.
    Old to_blob() (pre-commit) had an explicit `ValueType::Text => Some(txt.as_bytes().to_vec())` arm that was removed.
    The added regression test `test_sqlite3_value_blob_use_after_free` (sqlite3/tests/compat/mod.rs:2645) only binds/reads a 4-byte BLOB — the TEXT-via-value_blob path is untested.
    SQLite oracle: sqlite3_value_blob on a text value is non-NULL and returns the text bytes.

## [A44-2] Expression-depth limit (MAX_EXPR_DEPTH = 100) rejects valid queries SQLite accepts and Turso previously ran
- commit: 18ba9c9c "sqlite/parser: bound expression depth to prevent translator stack overflow" (2026-07-03)
- file: sqlite/parser/src/parser.rs:189 (MAX_EXPR_DEPTH), :~1370 & :~2073/2467 (enforcement in parse_expr / parse_expr_inner)
- at-head: present
- category: sql-semantics
- severity: medium
- confidence: high
- description: The commit adds two guards to prevent translator stack overflow on deep expressions: a recursion-depth counter (`expr_nesting_depth`) and a tree-height counter (`last_expr_height`, catches iteratively-parsed left-deep chains like `a OR b OR c ...`). The guard logic itself is correct (counters decrement on the error path; height folding is threaded through CASE/function/window/between/like/in/etc.; no arithmetic overflow since capped at 100). The concern is the chosen limit: `MAX_EXPR_DEPTH = 100`, an order of magnitude below SQLite's default `SQLITE_MAX_EXPR_DEPTH = 1000`. A chained boolean condition of ~100 terms — common in machine-generated SQL — now fails to parse. Before this commit there was no limit, so such queries parsed and ran (100 levels is far within an 8 MiB stack). This is an intentional tradeoff (reject-over-crash, documented in the code comment because the recursive translator uses larger stack frames), but the 100 threshold is aggressive enough to reject real, previously-working, SQLite-compatible queries.
- failure: `SELECT 1 WHERE 1=1 OR 1=1 OR ... (100 terms)` → Turso: `Parse error: Expression tree is too large (maximum depth 100)`; SQLite: returns `[(1,)]`. Reproduced against target/debug/tursodb. Boundary: a 99-term equality OR chain succeeds (tree height 100), a 100-term chain fails (height 101 > 100). Note IN-lists are unaffected (flattened to height 2), so this specifically bites long chained binary operators (OR/AND/+/…) and deeply nested expressions.
- evidence: |
    sqlite/parser/src/parser.rs:189 `pub const MAX_EXPR_DEPTH: usize = 100;` (present at 5f6098a0:sqlite/parser/src/parser.rs:189).
    Enforcement: parse_expr increments/checks expr_nesting_depth; parse_expr_inner maintains result_height and returns `Error::ParseError("Expression tree is too large ...")` when `result_height > MAX_EXPR_DEPTH`.
    Repro transcript (scratch W2A44):
      n=99  -> `1`
      n=100 -> `× Parse error: Expression tree is too large (maximum depth 100)`
      n=101 -> `× Parse error: ...`
      python3 sqlite3 (3.45.x) accepts the 150-term form: `[(1,)]`.
