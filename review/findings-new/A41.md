# Batch A41 review

No introduced defects found. Every substantive commit in the batch was
diff-read at its SHA, traced through callers, checked for survival at HEAD
(5f6098a0 / working tree bad083fa), and differentially tested against SQLite
3.45.1 where behavior was SQL-observable. All matched. Details of what was
checked (and ruled out) are below.

## [A41-1] (RULED OUT) OP_Eq REAL-affinity coercion — special lead
- commit: a92c7d3b "core/vdbe: don't realify integers in OP_Eq REAL-affinity coercion" (2026-05-05)
- file: core/vdbe/affinity.rs:267 (`convert_for_compare`), core/vdbe/execute.rs:1076
- at-head: present
- category: type coercion/affinity
- severity: n/a
- confidence: high
- description: New `convert_for_compare` applies numeric affinity only to TEXT
  operands for Numeric/Integer/Real affinity (matching SQLite's
  `applyNumericAffinity(x,0)` on strings only). Only the Real arm changed vs old
  `convert` (which realified integers). Int-vs-float then routes through
  `Numeric::cmp` -> `sqlite_int_float_cmp`, a faithful port of
  `sqlite3IntFloatCompare` (verified boundary handling of +/-2^63, NaN, exact
  tie via `int_as_float.partial_cmp`).
- failure: none. Differential tests all matched SQLite:
    - `CREATE TABLE t(c REAL); INSERT ... 1367756182.0*-1367756182; SELECT c=-1870756973399217200,...` -> `0|0|1` both engines (scan AND with index on c: 0 rows both).
    - `intcol=2.0 / =2.5`, `1=1.0`, `2=2.0`, `9007199254740993=9007199254740992.0` -> match.
    - Index seek on INTEGER col with float key `c=2.0 / c=2.5` -> match.
    - Text operand w/ REAL affinity `c='2' / '2.0' / 'abc'` -> match.
  The related cross-type index-seek fix is a separate later commit 8f58d4f5
  (not in this batch); at HEAD scan and seek are consistent.

## [A41-3] (RULED OUT) Prevent BEGIN IMMEDIATE with existing BEGIN CONCURRENT — special lead
- commit: c4497e43 (2026-05-05)
- file: core/vdbe/execute.rs:4562 (`op_auto_commit`)
- at-head: present (further hardened by later poison/StatementsInProgress commits)
- category: transaction lifecycle
- description: Rewrote op_auto_commit tx-op dispatch. `valid_transition` = BEGIN
  only when had_autocommit, COMMIT/ROLLBACK only when in a txn. BEGIN returns early
  (no longer falls through to `commit_txn` as the old code did). All BEGIN variants
  (Deferred/Immediate/Concurrent) emit the same `AutoCommit{auto_commit:false}`
  (verified in translate/transaction.rs), so after BEGIN CONCURRENT auto_commit=false
  and a following COMMIT is a valid transition. Tail (savepoint/FK/CDC clears) is
  reached only for COMMIT/ROLLBACK now, so dropping the old `is_commit||is_rollback`
  guards is behavior-preserving.
- failure: none. Verified with MVCC (`PRAGMA journal_mode='MVCC'`):
    - BEGIN CONCURRENT; INSERT; COMMIT -> persists (count 2).
    - BEGIN CONCURRENT; INSERT; ROLLBACK -> not persisted (count 0).
    - BEGIN CONCURRENT; BEGIN IMMEDIATE -> "cannot start a transaction within a transaction".
  WAL error paths match SQLite exactly: COMMIT/ROLLBACK with no tx, BEGIN;BEGIN,
  and normal BEGIN/COMMIT + BEGIN/ROLLBACK round-trips.

## [A41-8] (RULED OUT) Invalid changes() count when CDC enabled
- commit: 995fb0ab (2026-06-02)
- file: core/vdbe/execute.rs (op_insert/op_delete), core/vdbe/mod.rs
  (record_statement_change/record_total_change, n_total_change)
- at-head: present
- category: changes()/total_changes()
- description: Splits statement change count (`n_change`, drives changes()) from
  total change count (`n_total_change`, drives total_changes()). CDC inserts carry
  new `SKIP_STATEMENT_CHANGE_COUNT` flag -> `record_total_change` only, so they no
  longer inflate changes(). `set_changes` no longer bumps total; every former caller
  now also calls `add_total_changes`. Error/reset paths that used
  `set_changes_without_total(x)` now use `set_changes(x)` (identical semantics).
  finish_subprogram uses n_total_change for the total add.
- failure: none. Non-CDC changes()/total_changes() exact across INSERT/DELETE/UPDATE
  (3|3, 2|5, 2|7, 3|10) and with a trigger (1|2, 2|6) — both match SQLite. With CDC,
  changes() correctly excludes CDC rows (=1 / =3). total_changes() with CDC includes
  CDC rows, which equals the pre-fix behavior (no regression) and has no SQLite oracle.

## Batch summary
Reviewed all 20 commits (3 special leads + 17 others). No introduced defects.
All three leads (OP_Eq REAL-affinity coercion, RENAME COLUMN expression-index
rewrite, BEGIN-IMMEDIATE-within-CONCURRENT) are faithful fixes verified against
SQLite, including int-vs-float precision, index seeks, and MVCC BEGIN CONCURRENT
commit/rollback/nesting. The larger op_auto_commit rewrite, the changes()/CDC
split, the recursive-FK-cascade subprogram conversion, the fallible-allocation
migrations, and the MVCC statement-lifecycle abort/halt changes were all traced
and shown behavior-preserving for shared (non-MVCC) paths. One SQLite divergence
was observed (generic runtime error inside an explicit BEGIN rolls back the whole
txn) but it is pre-existing OLD-abort() behavior, not introduced by this batch.
