# Batch A43 findings

## [A43-1] Reading a SQLite-created DB with invalid-UTF-8 TEXT now hard-errors ("Corrupt")
- commit: ee89a2217171efb6209dd9e2bdb49f26fd2fbd76 "core: reject invalid UTF-8 in TEXT record payloads" (2026-07-29)
- file: core/storage/sqlite3_ondisk.rs:1091 and :1221 (`read_value` / `read_value_serial_type`)
- at-head: present (`git log 1088-area` unchanged; current code uses `simdutf8::basic::from_utf8(...).map_err(|_| Corrupt(...))`)
- category: SQLite file-format compatibility / coercion
- severity: low
- confidence: medium
- description: The TEXT record decoders were changed from `from_utf8_unchecked` to a validating `simdutf8::from_utf8`, which returns `LimboError::Corrupt("TEXT value contains invalid UTF-8")` on any non-UTF-8 TEXT payload. SQLite tolerates TEXT values that are not valid UTF-8 (they can be produced legitimately, e.g. `CAST(x'41ff42' AS TEXT)`), so a database created/written by SQLite that contains such a value can no longer be read by turso: any query whose scan reaches that row aborts the whole statement. This is a genuine, reproducible SQLite-file-compatibility regression versus both SQLite and pre-commit turso. NOTE: it looks intentional (the commit adds a test asserting the Corrupt error) and it replaces prior Undefined Behavior (`from_utf8_unchecked` on invalid bytes); turso never produces invalid-UTF-8 TEXT itself (CAST/char() sanitize surrogates and invalid bytes to U+FFFD), so there is no self-inflicted crash. Reported so a human can decide whether the compatibility cost is acceptable.
- failure: |
    # Create a DB with SQLite (invalid-UTF-8 TEXT is accepted):
    python3 -c "import sqlite3; c=sqlite3.connect('ext.db');
      c.execute('CREATE TABLE t(id INTEGER PRIMARY KEY, s)');
      c.execute(\"INSERT INTO t VALUES (1, CAST(x'41ff42' AS TEXT))\");
      c.execute(\"INSERT INTO t VALUES (2,'valid')\"); c.commit()"
    # SQLite reads it fine: hex(s) for id=1 -> '41FF42', typeof -> 'text'
    # turso aborts the entire scan:
    $ printf '.mode list\nSELECT id, typeof(s) FROM t;\n' | tursodb -q ext.db
    Runtime error: Corrupt database: TEXT value contains invalid UTF-8 (11)   # EXIT=1
    # (even though row id=2 is valid, the full-table scan hits row 1 and errors out)
- evidence: |
    core/storage/sqlite3_ondisk.rs (post-commit):
      let val = simdutf8::basic::from_utf8(data).map_err(|_| {
          mark_unlikely();
          LimboError::Corrupt("TEXT value contains invalid UTF-8".into())
      })?;
    Repro transcript above; SQLite 3.45.1 reads the same file without error.
    Confirmed turso does NOT produce such data itself:
      SELECT hex(char(55296)) -> EFBFBD (U+FFFD) on turso vs EDA080 on SQLite;
      INSERT ... CAST(x'ff' AS TEXT) stores EFBFBD (sanitized), round-trips fine.
