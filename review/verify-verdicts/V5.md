## VERDICT [A09-1] External aggregate called with wrong arg count reports "no such function" instead of "wrong number of arguments"
- verdict: CONFIRMED
- severity: low
- repro: yes (transcript below)
- reasoning: Reproduced at HEAD: `SELECT median(1,2)` and `SELECT percentile(1)` both return "Parse error: no such function: <name>", even though both are registered external aggregates. median (core/percentile.rs:20 `const ARGS: i32 = 1`) and percentile (line 54 `const ARGS: i32 = 2`) are managed aggregates registered via `AggregateDerive`, which passes the fixed `ARGS` argc to `register_aggregate_function` (macros/src/ext/agg_derive.rs:81). At HEAD `ExtFunc::matches_arg_count` enforces that argc for the Aggregate arm (core/function.rs:110 `*argc < 0 || *argc as usize == arg_count`), and `SymbolTable::resolve_function` filters candidates through it (core/connection.rs:5111 `.filter(|func| func.func.matches_arg_count(arg_count))`), so a fixed-arity aggregate invoked with the wrong count resolves to None and name resolution falls through to "no such function". The regression is real and correctly bracketed: the parent of the managed-aggregate change had `Self::Aggregate { .. } => true` (git show 2cbc2d13^:core/function.rs line 59), so wrong-arity used to resolve and then bail with the clearer "External aggregate function called with wrong number of arguments" (still present but now unreachable for fixed-arity aggregates at core/translate/aggregation.rs:657-662). SQLite's convention: known function + wrong arity -> "wrong number of arguments to function X()", unknown -> "no such function"; turso's own built-in `avg(1,2)` correctly says "wrong number of arguments to function avg()", so external aggregates now diverge from BOTH SQLite and turso's own built-ins. Valid-arity calls are unaffected (median(x)=2.0, percentile(x,50)=2.0). Purely an error-message-quality regression on a user-misuse path: no wrong results, no crash -> low severity confirmed. (Attribution nuance: the finding cites merge 2cbc2d13 "Add managed aggregate callback support"; `git log -S` puts the actual line-introducing commit at a4fab8ff "Add managed aggregate callbacks" on the merged branch. Does not affect the verdict.)
- repro-transcript: |
    $ SELECT median(1,2);      -> "Parse error: no such function: median"   (EXIT 1)
    $ SELECT percentile(1);    -> "Parse error: no such function: percentile" (EXIT 1)
    $ CREATE TABLE t(x); INSERT INTO t VALUES(1),(2),(3);
      SELECT median(x) FROM t;      -> 2.0   (EXIT 0)
      SELECT percentile(x,50) FROM t; -> 2.0 (EXIT 0)

## VERDICT [A15-1] regexp() admits 1 argument then indexes args[1] -> process abort
- verdict: FIXED-AT-HEAD (fixed by 530627ef)
- severity: medium (as the historical bug; not present at HEAD)
- repro: yes (transcript below - HEAD now errors cleanly, no abort)
- reasoning: The pre-fix code at b756295e guarded arity with `if !(1..=2).contains(&args.len())`, which admits exactly 1 argument and then unconditionally indexes `args[1]` (git show b756295e:core/regexp.rs). regexp is registered variadically (argc -1, core/ext/mod.rs:105 passes -1 to register_scalar_function), so a 1-arg call passes name resolution and reaches the shim; the OOB slice index panics, and a panic crossing the generated `extern "C"` boundary aborts the process. The fix is 530627ef "core/regexp: require exactly two arguments" — the ONLY commit touching core/regexp.rs since b756295e (git log --oneline b756295e..5f6098a0 -- core/regexp.rs) — which also added the `regexp_rejects_wrong_arity` test whose comment confirms reachability ("argc == 1 used to be admitted and then index args[1], aborting"). The HEAD repro reaching the internal `args.len() != 2` guard proves the 1-arg call does reach regexp(), confirming the pre-fix path was live. Bug was real between 2026-03-16 and 2026-07-28; fixed at HEAD.

## VERDICT [A15-2] regexp() coerces REAL with Rust f64::to_string ("2") diverging from SQLite text coercion ("2.0")
- verdict: CONFIRMED
- severity: low
- repro: yes (transcript below)
- reasoning: At HEAD `Value::to_text_coerced` renders Float via `self.to_float().map(|f| f.to_string())` (extensions/core/src/types.rs:327); Rust's f64::to_string prints a whole float as "2", not "2.0". Reproduced: for a REAL column holding 2.0, turso gives `x REGEXP '^2$'` -> 1 and `x REGEXP '^2\.0$'` -> 0, but turso's OWN `CAST(x AS TEXT)` yields "2.0", so `CAST(x AS TEXT) REGEXP '^2\.0$'` -> 1 and `CAST(x AS TEXT) REGEXP '^2$'` -> 0. That is a self-inconsistency: `x REGEXP p` and `CAST(x AS TEXT) REGEXP p` return opposite answers for the same whole float. SQLite's convention (CAST(2.0 AS TEXT) = "2.0", and ext/misc/regexp.c operates on sqlite3_value_text which renders REAL 2.0 as "2.0") gives the exact inverse of turso: `x REGEXP '^2$'` -> 0, `x REGEXP '^2.0$'` -> 1. This is a silent wrong result, but the blast radius is narrow: `to_text_coerced` is used ONLY by regexp (both callers are core/regexp.rs:17,20), and only whole-number REALs (and scientific-notation values) diverge — fractional floats like 3.14 render identically, which is why the commit's own `.sqltest` coverage (only 3.14/45.6/-1.5) missed it. Narrow scope -> low severity. Confirmed present at HEAD.
- repro-transcript: |
    turso (CREATE TABLE t(x REAL); INSERT INTO t VALUES(2.0);):
      x REGEXP '^2$'                -> 1
      x REGEXP '^2\.0$'             -> 0
      CAST(x AS TEXT)               -> 2.0
      CAST(x AS TEXT) REGEXP '^2\.0$' -> 1
      CAST(x AS TEXT) REGEXP '^2$'  -> 0
    SQLite oracle:
      CAST(2.0 AS TEXT)             -> '2.0'
      value_text-based regexp: x REGEXP '^2$' -> 0 ; x REGEXP '^2.0$' -> 1  (inverse of turso)
    grep to_text_coerced -> only core/regexp.rs:17 and :20 (blast radius = regexp only)
