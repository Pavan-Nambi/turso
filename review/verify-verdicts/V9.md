## VERDICT [A23-1] Row-value IN/NOT IN ignores NULL in non-first tuple components (silent wrong results)
- verdict: CONFIRMED
- severity: high
- repro: yes
- reasoning: The cited mechanism is real and present at reviewed HEAD 5f6098a0. `translate_in_list` (core/translate/expr/condition.rs:63-91) builds its NULL tracker `check_null_reg` only from component 0: it inits `BitAnd(lhs_reg, lhs_reg)` (lhs_reg is the first register of the LHS tuple) and folds in only `rhs_reg` (first register of each RHS tuple). The row-value comparison path (lines 127-183) compares every component `lhs_reg+j`/`rhs_reg+j`, but the final 3VL decision (lines 186-193: `IsNull check_null_reg -> when_null` else `Goto when_false`) consults only that component-0 tracker, so a NULL in component 1..n is invisible. For `(1,NULL) IN ((1,2))`: component 0 (1=1) matches so the row is not skipped, the last-component `Eq(NULL,2)` does not jump to the match label (no jump_if_null), and check_null_reg = BitAnd(1,1)=1 (not NULL) -> result FALSE instead of the correct NULL. The expression-context caller (core/translate/expr/translator.rs:2740-2752) passes distinct false/null labels, so check_null_reg is allocated and this path is exercised. No later fix: the only two commits touching condition.rs since 98b46b15 are 078f6f5f (IS-TRUE truth test, unrelated) and 96d4dab9 (module split, code moved verbatim); `git log -S check_null_reg 98b46b15..5f6098a0` returns only the module-split commit. Live repro matches the oracle on all four cited cases, including the correct control `(2,NULL) NOT IN ((1,2))=1`. Kept at high: silent wrong query results, but confined to the row-value IN/NOT-IN-with-NULL-in-a-non-first-component case.

## VERDICT [A32-1] Partial index on the preserved (left) table of an OUTER JOIN silently drops rows
- verdict: CONFIRMED
- severity: critical
- repro: yes
- reasoning: The defect is present at reviewed HEAD 5f6098a0 (guard verified identical via `git show 5f6098a0:core/translate/optimizer/constraints.rs`). `partial_index_predicate_terms`'s `can_use_query_term` guard (constraints.rs:1470-1481) early-returns `true` when `table_reference.join_info` is `None`. For `t LEFT JOIN s ON t.b>0`, the join_info attaches to the right table `s`; the preserved left table `t` has `join_info == None`, so every query term is accepted — including the ON term `t.b>0` whose `from_outer_join == Some(s)`. That term is syntactically equal to the partial index predicate `b>0`, so `partial_index_predicate_terms` returns Some, `can_use_partial_index` returns true, and the empty-refs partial index is retained as a scan driver (retain guard at constraints.rs:1131-1136 and candidate push at 1108-1109). Driving the scan of the preserved table through `partial_t ON t(a) WHERE b>0` visits only rows with b>0, silently dropping the b<=0 rows that a LEFT JOIN must still emit null-padded. This is the exact hole the reviewer described: the guard handles is_full_outer() and is_outer() but not the None case of the preserved side. No later fix: the bug reproduces in the working-tree debug binary, which already contains every constraints.rs commit in 9cbc321d..5f6098a0 (the 5 commits between working tree and 5f6098a0 do not touch this area), and none of them (incl. 5ddba9f3 FULL-JOIN null-extend, 8dc8312f outer-join predicate application, ab18098d predicate consumption) altered the None-join_info acceptance. EXPLAIN confirms `SCAN t USING INDEX partial_t`. Silent row loss from an ordinary LEFT-JOIN + partial-index schema -> critical.
