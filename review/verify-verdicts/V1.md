## VERDICT [A08-1] HAVING aliased-aggregate misuse check rejects valid SQL when a real column shares the alias name
- verdict: CONFIRMED
- severity: medium
- repro: yes
- reasoning: The check at core/translate/select.rs:1934-1951 (`find_aliased_aggregate_ref`) fires whenever a bare identifier inside a HAVING aggregate matches an aggregate result-column alias, without ever checking whether that identifier also names a real FROM-clause column. SQLite's name resolution gives real table columns precedence over result-column aliases, so `max(c)` resolves to column `t.c` (not the alias) and the query is valid. I ran the finding's example on both engines: tursodb raises `Parse error: misuse of aliased aggregate c`, real SQLite 3.45.1 returns rows. The negative control (no real column `c`, so `c` resolves to the alias) errors in BOTH engines, proving the difference is exactly the missing column-shadowing check. Code is byte-identical at reviewed HEAD 5f6098a0 and no later commit touched the check (`-S` finds only an unrelated TLA+ spec). Error-path only (rejects valid SQL, no data risk), hence medium.
- repro-transcript: |
    $ printf '.mode list\nCREATE TABLE t(a, c);\nINSERT INTO t VALUES (1,5),(1,7),(2,3);\nSELECT count(*) AS c, a FROM t GROUP BY a HAVING max(c) > 0;\n' | tursodb -q test.db
      × Parse error: misuse of aliased aggregate c
    # oracle (real SQLite 3.45.1), same schema/query:
      [(2, 1), (1, 2)]

## VERDICT [A08-3] progress handler callback runs while sqlite3_step holds the non-reentrant handle mutex — reentrant API call deadlocks
- verdict: FIXED-AT-HEAD (fixed by 9710f11ada58ba83f7540192b2f1224a6b1b02a7)

So the defect is not live at HEAD. Medium reflects the pre-fix impact (hang, not corruption).

## VERDICT [A08-4] PRAGMA ignore_check_constraints never invalidates prepared statements — stale cached statements skip (or keep enforcing) CHECK constraints
- verdict: CONFIRMED
- severity: medium
- repro: yes (SQLite divergence + CLI fresh-prepare proven; live reused-statement turso repro needs a Rust build, not run)
- reasoning: The full chain is verified end-to-end. `emit_check_constraints` bakes the pragma decision at compile time (core/translate/emitter/mod.rs:2283 short-circuits when `check_constraints_ignored()`). A reused statement reprepares only when `PrepareContext::matches_connection` returns false (core/statement.rs:523-532), and that function compares only `database_ptr` + `generation` (core/vdbe/mod.rs:1594-1597). `set_check_constraints_ignored` (core/connection.rs:1899-1902) does NOT call `bump_prepare_context_generation()`, unlike every analogous compile-affecting setter — e.g. `set_foreign_keys_enabled` (line 1892) and `set_query_only` (line 3824) both bump. So flipping `ignore_check_constraints` leaves the generation unchanged → no reprepare → stale bytecode. I confirmed no catch-all bump exists (the other bump sites are cache_spill / schema-restore / attached-schema specific). The oracle proves SQLite honors the flip for a reused prepared statement in BOTH directions (C program: OFF→ON makes a previously-rejected INSERT succeed; ON→OFF makes a previously-accepted INSERT fail). turso's fresh-prepare path is correct (CLI: each re-prepared INSERT reflects the current pragma), which pins the divergence to reused/cached statements — reachable via `prepare_cached` (present in core and bindings/rust) or any long-lived reset+re-run `Statement`. The passing test `test_prepare_cached_reprepare_on_query_only_change` proves the reprepare mechanism works for a bumping pragma (query_only), making check_constraints the sole non-bumping compile-affecting pragma. Attribution (accurate in the finding): the old value-compare PrepareContext also lacked a check_constraints field (verified at 79d7435^), so the gap predates the cited commit (dates to 7cb4b65a) — the defect is live at HEAD but was preserved, not introduced, by 79d7435. Direction B (compiled ON, flip OFF) silently inserts a CHECK-violating row → medium; exposure is narrow (needs statement caching + runtime pragma flip).
