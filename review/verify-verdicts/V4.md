## VERDICT [A12-1] JSONB parent-size bookkeeping double-adds delta for consecutive array ancestors — errors and silent persisted corruption on nested-array paths
- verdict: CONFIRMED
- severity: critical
- repro: yes
- reasoning: Fully reproduced with exact byte matches on both engines. `update_parent_references` (core/json/jsonb.rs:2539-2558) updates the array-element header (`arr_el_size + delta`) for every ARRAY stack entry with no `is_prev_arr` guard. For two adjacent array stack entries, the outer entry's `get_array_index()` points at the same header the inner entry already rewrote (with delta folded in) as its own container header, so `delta` is added to it a second time. Confirmed the guard was removed in inner commit 1fa653b8 (diff shows `-if el_type == ElementType::ARRAY && !is_prev_arr` → `+if el_type == ElementType::ARRAY`, and the `else { is_prev_arr = false }` deleted). No later commit in `git log 23c15006..5f6098a0 -- core/json/` restores it; code is byte-identical at reviewed HEAD 5f6098a0. Manifests three ways exactly as claimed: hard error on json_set/json_remove, swallowed SQL NULL on json_insert, and a silently-corrupted JSONB blob from jsonb_set/jsonb_remove whose middle array header claims the wrong size (BB=11 vs 7B=7; 1B=1 vs 3B=3). End-to-end GeoJSON store-then-read destroys the persisted document. This is the worst class: silent on-disk corruption of a valid document via ordinary UPDATE. Crown-jewel critical stands.
- repro-transcript: |
    # turso (debug binary, working tree = json identical to reviewed HEAD 5f6098a0)
    json_set('[[[1]]]','$[0][0][0]','short')       => Runtime error: Parse error: Failed to read header byte
    json_insert('[[[1]]]','$[0][0][1]',2)          => <SQL NULL>
    hex(jsonb_set('[[[1]]]','$[0][0][0]','short')) => 8BBB6B5773686F7274
    hex(jsonb_remove('[[[1,2]]]','$[0][0][1]'))    => 4B1B2B1331
    # end-to-end (store then read):
    CREATE TABLE t(id INTEGER PRIMARY KEY, j BLOB);
    INSERT INTO t VALUES (1, jsonb('{"geometry":{"coordinates":[[[1,2],[3,4]]]}}'));
    UPDATE t SET j = jsonb_set(j, '$.geometry.coordinates[0][0][0]', 99.5);  -- succeeds
    SELECT json(j) FROM t;                          => Runtime error: Parse error: malformed JSON

    # SQLite 3.45.1 (oracle) — all correct:
    json_set('[[[1]]]','$[0][0][0]','short')       => [[["short"]]]
    json_insert('[[[1]]]','$[0][0][1]',2)          => [[[1,2]]]
    hex(jsonb_set('[[[1]]]','$[0][0][0]','short')) => 8B7B6B5A73686F7274   (middle array 7B=size7, turso wrote BB=size11)
    hex(jsonb_remove('[[[1,2]]]','$[0][0][1]'))    => 4B3B2B1331           (middle array 3B=size3, turso wrote 1B=size1)
    UPDATE + json(j)                               => {"geometry":{"coordinates":[[[99.5,2],[3,4]]]}}

## VERDICT [A12-2] JSON-null early return in json_string_to_db_type hijacks String/Binary output variants — json_set/jsonb_set family returns SQL NULL for top-level JSON null documents
- verdict: CONFIRMED
- severity: medium
- reasoning: Confirmed in code and by repro. core/json/mod.rs:619-621 (identical at reviewed HEAD) places `if element_type == ElementType::NULL { return Ok(Value::Null); }` above both the Binary (622) and String (626) early returns, so any function serializing through String/Binary maps a top-level JSON-null document to SQL NULL. SQLite returns the text `null` (String variant) or the blob `X'00'` (Binary variant) instead. Divergence is real even within turso: `json('null')` returns text `null` and `->>`/`->` return `null`, while json_set('null',...) returns SQL NULL. The end-to-end UPDATE data-loss shape reproduces: a row whose valid document is `null` is silently overwritten with SQL NULL. Medium is right — silent wrong result / data loss, but only on the narrow top-level-JSON-null document case.
- repro: yes
- repro-transcript: |

    json_replace('null','$.a',1)    => <NULL>   (SQLite: 'null')

    json_remove('null','$.a')       => <NULL>   (SQLite: 'null')

## VERDICT [A12-4] Array-append navigation drops the placeholder delta from the immediate container header — jsonb_set/jsonb_insert with $[#] (and append-at-end index) return invalid JSONB
- verdict: CONFIRMED
- severity: high
- reasoning: Confirmed in code and by exact-byte repro. The `$[#]` None arms (jsonb.rs:2660-2675 root-array, 2853-2868, 3041-3060 key[#]) splice a 1-byte placeholder and record it as `target.delta=1`. In SetOperation::execute (jsonb.rs:369-384) the immediate container header is rewritten as `obj_value_size + delta` only — `target.delta` (the placeholder byte physically inside this container) is added solely to ancestors via `update_parent_references(stack, target.delta + delta + h_delta)`. So the appended-to array/object header is short by exactly 1 byte. Every claimed hex matches: `7B` vs SQLite `8B`; nested inner `3B` vs `4B`; append-by-index `[1]$[1]` → `3B...` vs `4B...`; empty `[]$[0]` → `1B1331` vs `2B1331`. turso's own json() then cannot parse the blob. Also true for the pre-existing Some(idx) append-at-end path. One wording nuance: the finding says "every later json(j) fails" on the stored row — accurate for jsonb_set and root-array shapes (json() → parse error), but for jsonb_insert on a nested object the manifestation is instead SILENT DATA LOSS: the operation errors internally, InsertOperation swallows it via `let _ = operate_on_path(...)` (ops.rs:112 etc.), and the original blob is returned with the appended element gone. Both outcomes are wrong vs SQLite; core defect fully confirmed. High severity (data corruption / silent data loss; not critical only because it corrupts the edited container, not an unrelated sibling as in A12-1).
- repro: yes
- repro-transcript: |
    # turso (direct):
    hex(jsonb_set('[1,2,3]','$[#]',4))        => 7B1331133213331334   (SQLite: 8B1331133213331334)
    json(jsonb_set('[1,2,3]','$[#]',4))       => Runtime error: Parse error: Expected : after object key  (SQLite: [1,2,3,4])
    hex(jsonb_set('{"a":[1]}','$.a[#]',2))    => 7C17613B13311332     (SQLite: 7C17614B13311332)
    hex(jsonb_insert('[1,2,3]','$[#]',4))     => 7B1331133213331334   (SQLite: 8B...)
    hex(jsonb_set('[1]','$[1]',2))            => 3B13311332           (SQLite: 4B13311332)
    hex(jsonb_set('[]','$[0]',1))             => 1B1331               (SQLite: 2B1331)
    # end-to-end store-then-read:
    # root array via jsonb_set: stored 7B1331133213331334 ; json(j) => Runtime error: parse error  (json_extract too)
    # nested via jsonb_insert:  stored 8C47746167732B1761 (== ORIGINAL, "x" dropped); json(j) => {"tags":["a"]} ; json_extract(j,'$.tags[1]') => <NULL>  (silent data loss)

## VERDICT [A12-5] Bracket-quoted JSON path on an array node returns NULL where SQLite raises "bad JSON path"
- verdict: CONFIRMED
- severity: low
- reasoning: Primary claim confirmed on both engines. path.rs:338 parses `$["key"]`/`$['key']` into `PathElement::BracketQuotedKey`; the `_ =>` arm at jsonb.rs:3064-3067 (comment: "never matches, falls through to Not found → NULL") returns NULL for ALL node types, so an array node with a bracket-quoted token cannot error. `json_extract('[1,2]','$["0"]')` → turso NULL vs SQLite ERR "bad JSON path" — exact match with the finding's oracle line, and the object case `$["key"]` is NULL on both (as the finding states). This behavior is intentional per commit 69bb40eb but is over-broad for arrays, so it is not fixed at HEAD; code identical at reviewed HEAD. One imprecision in the finding's *description*: the "turso additionally accepts single-quoted bracket keys ($['key']) that SQLite rejects at the SQL level" framing is misleading — SQLite returns NULL (no rejection) for `$['key']` on an OBJECT; SQLite only errors on the ARRAY case, for BOTH quote styles. The divergence is node-type-based (array), not quote-style-based. The finding's core failure line and evidence oracle are exactly right, so CONFIRMED at low severity (error-path divergence: silent NULL where SQLite raises an error).
- repro: yes
- repro-transcript: |
    # turso:                                          # SQLite 3.45.1:
    json_extract('[1,2]','$["0"]')     => <NULL>      => ERR bad JSON path: '$["0"]'
    json_extract('{"key":1}','$["key"]')=> <NULL>     => NULL   (match)
    json_extract('{"key":1}','$[''key''])=> <NULL>    => NULL   (match; not an error in SQLite)
    json_extract('[1,2]','$[''0''])     => <NULL>     => ERR bad JSON path: '$[''0'']'
