## VERDICT [A10-1] repeat()/lpad()/rpad() allocate attacker-controlled length with no limit -> process abort/OOM from plain SQL
- verdict: CONFIRMED
- severity: high
- repro: yes
- reasoning: The defect is real and live at reviewed HEAD (5f6098a0). `git log c681ded..5f6098a0 -- core/functions/string.rs` is EMPTY, so the introducing code is unchanged. `exec_repeat` (string.rs:31) calls `s.repeat(n as usize)` and `pad` (string.rs:88-92) does `.cycle().take(target_len - char_count).collect::<String>()` with the count taken straight from the SQL argument (i64, floats saturated via `f as i64`), with NO length check and NO fallible allocation. The VDBE dispatch (execute.rs:10058-10083) passes the raw register values through with no pre-check, so any plain SQL statement reaches this. Contrast the project's own norm: `zeroblob`/`randomblob` (value.rs:323-327, 918-922) guard `length > MAX_BLOB_LENGTH (1_000_000_000)` -> `LimboError::TooBig` via `try_vec!`. I proved the divergence three ways at runtime: (1) `zeroblob(1000000001)` returns a graceful "string or blob too big" error while `repeat('a', 1050000000)` happily builds a 1.05 GB string (past the 1 GB blob cap) with no error; (2) `repeat('ab', i64::MAX)` panics "capacity overflow" (len*n exceeds isize::MAX) straight through `exec_repeat` -> `op_function` -> VDBE -> CLI with NO catch_unwind on the path (the only catch_unwind sites are tests + statement.rs reset()), exit 101; (3) `lpad('x', i64::MAX)` hits Rust's `handle_alloc_error` -> SIGABRT (exit 134), which is uncatchable regardless of panic strategy. Note `panic = "abort"` is set for the release/release-official/antithesis/fuzzing profiles (Cargo.toml:183,205,211), so in a production build even case (2)'s panic is an immediate SIGABRT, not an unwind. Net: a single plain-SQL statement aborts the whole process embedding turso_core (killing in-flight transactions), where a catchable "too big" error was both expected and trivially available. Severity high: trivially-triggered one-statement process-abort DoS; kept below critical because it is a clean crash, not silent corruption.

## VERDICT [A10-2] gcd()/lcm() panic on (i64::MIN, -1) via i64::MIN % -1 remainder overflow
- verdict: FIXED-AT-HEAD (fixed by e08485d6)
- severity: medium
- repro: yes
- reasoning: The bug was real at the introducing commit c681ded: `gcd_inner` bailed only on `a==0 || b==0 || a==b` before doing `a %= b` / `b %= a`, so the pair (i64::MIN, -1) evaluated `i64::MIN % -1`, which rustc guards unconditionally (panic "attempt to calculate the remainder with overflow", even in release). But the fix is genuinely present at both working-tree HEAD (bad083fa) and reviewed HEAD (5f6098a0): math.rs:23-25 now has `if a == -1 || b == -1 { return Some(1); }` placed before the reduction, plus regression tests `gcd_min_by_minus_one` / `lcm_min_by_minus_one` (math.rs:145-169). `git log c681ded..5f6098a0 -- core/functions/math.rs` shows exactly one commit, e08485d6 ("core/functions: fix gcd/lcm overflow on i64::MIN % -1"), and `git merge-base --is-ancestor e08485d6 5f6098a0` (and bad083fa) both return true. Live repro confirms no panic at HEAD: gcd returns 1 for both argument orders, lcm surfaces a graceful "integer overflow" error (its 2^63 result is unrepresentable) rather than crashing. The finding's own `at-head: fixed-by e08485d6` classification is correct. Severity medium reflects the historical crash (matches the finding).

## VERDICT [A10-3] datetime numeric-string whitespace trim omits vertical tab, diverging from SQLite
- verdict: CONFIRMED
- severity: low
- repro: yes
- reasoning: Live at reviewed HEAD (5f6098a0): datetime.rs:222 is `let numeric_value = value.trim_matches(|c: char| c.is_ascii_whitespace());` (git show confirms the line is byte-identical at 5f6098a0; the six later datetime.rs commits don't touch it). Rust's `char::is_ascii_whitespace` is exactly {0x09, 0x0A, 0x0C, 0x0D, 0x20} and deliberately EXCLUDES 0x0B (vertical tab); SQLite's `sqlite3AtoF` skips leading/trailing bytes via `sqlite3Isspace`, whose ctype map includes 0x0B. So for a numeric date/time string wrapped in a vertical tab, Turso's trim leaves the 0x0B, `parse::<f64>()` fails, every later parser rejects it, and the function returns NULL, whereas SQLite parses the number. Confirmed against the 3.45.1 oracle: SQLite returns -210866328000 for `'5'||char(11)` and `char(11)||'5'`; Turso returns NULL for both, while both engines agree on tab (char 9) and space (char 32) — pinpointing vertical tab as the sole diverging character. This is a silent data divergence (NULL vs a number) that matters in differential/replication/INSERT contexts, but it is one obscure whitespace byte and produces NULL rather than a wrong number or corruption, so severity low (matches the finding).
