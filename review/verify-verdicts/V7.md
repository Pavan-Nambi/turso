## VERDICT [A17-1] Named savepoints capture their WAL rollback position without any lock; ROLLBACK TO installs a stale/dead-generation position, corrupting WAL state and reader visibility
- verdict: FIXED-AT-HEAD (fixed by 46cd926d; earlier partial mitigation b8ae9ccf)
- severity: critical
- repro: yes (single-connection scenario at HEAD behaves correctly; the pre-fix bug cannot be run because only the HEAD binary exists)
- reasoning: >
    Bug was REAL at the introducing commit 2706498e. `open_savepoint_with_kind`
    (pager.rs:1856-1875 at that commit) captured `wal.get_max_frame()` /
    `wal.get_last_checksum()` with NO lock, and the non-MVCC `op_savepoint` Begin
    path (execute.rs:2637+) did only `open_subjournal`/`with_header`/
    `open_named_savepoint` — no `begin_read_tx`/`begin_write_tx`. So the position
    was the connection's private (possibly stale / pre-log-restart) snapshot.
    `Wal::rollback(Some(RollbackTo))` (wal.rs:1691-1717) then wrote that target
    into the SHARED state: `frame_cache.retain(|..| pop frames > max_frame)` prunes
    the shared frame cache, plus `self.max_frame.store(...)` / `last_checksum`.
    Both defects confirmed by reading the code at the commit.
    The fix is genuinely present at HEAD and covers the scenario: (a)
    `open_savepoint_with_kind` (pager.rs:2185-2193) captures `wal_pos` only when
    `wal.holds_write_lock()`, else `None`; (b) `materialize_savepoint_wal_positions`
    (pager.rs:3034) fills unmaterialized positions inside `begin_write_tx`
    (pager.rs:3026) AFTER `wal.begin_write_tx` — i.e. after the write upgrade and
    any `try_restart_log_before_write`, so positions belong to the current
    generation; (c) `rollback_to_snapshot` (pager.rs:2299) only rewinds the WAL
    when `wal_pos` is `Some`; (d) `Wal::rollback` (wal.rs:4098-4114) asserts
    `checkpoint_seq == current generation` AND `frame >= committed max_frame`,
    which directly rules out both the dead-generation and the
    behind-committed-frames (multi-connection frame-cache pruning) cases. Both
    46cd926d and b8ae9ccf are ancestors of HEAD (`git merge-base --is-ancestor`).
    Multi-connection variant is covered by (d): a savepoint position is captured
    only under the exclusive write lock at the current generation, so it can never
    be behind another connection's committed frames.
- repro-transcript: |
    # single-connection: backfilled WAL, SAVEPOINT, INSERT, ROLLBACK TO
    $ printf 'PRAGMA journal_mode=WAL; CREATE TABLE t(x); INSERT INTO t VALUES(0);
      PRAGMA wal_checkpoint(TRUNCATE); SAVEPOINT sp; INSERT INTO t VALUES(1);
      ROLLBACK TO sp; SELECT x FROM t; RELEASE sp; SELECT x FROM t;
      PRAGMA integrity_check;' | tursodb -q a171.db
    after-rollback:|0        # row 1 correctly rolled back
    after-release:|0
    ok                       # integrity ok
    == reopen fresh process ==
    reopen:|0
    ok
    == sqlite 3.45.1 oracle ==
    after-rollback [(0,)]     after-release [(0,)]   # identical

## VERDICT [A17-2] Savepoint operations permitted while a write statement is suspended mid-execution; ROLLBACK TO restores pages underneath the suspended writer
- verdict: FIXED-AT-HEAD (fixed by 59d03e62)
- severity: high
- repro: not-attempted (requires API-level mid-statement interleaving — step a write statement partially, e.g. INSERT...RETURNING or an I/O yield, then issue a savepoint op on the SAME connection; the CLI drains each statement fully so it cannot express this. Guard verified by code reading.)
- reasoning: >
    Bug was REAL at 2706498e: `op_savepoint` (execute.rs:2637-2737 at that commit)
    dispatched Begin/Release/RollbackTo straight into pager mutation
    (`pager.rollback_to_named_savepoint`, etc.) with no check of in-flight
    statements, and Turso has no SQLite-style cursor-tripping. Confirmed by reading
    the commit.
    The fix is present at HEAD (5f6098a0 execute.rs:4779-4792): before the match,
    `if !conn.is_nested_stmt() && conn.n_active_writes.load() > 0 { return
    Err(StatementsInProgress(...)) }` for all three ops (Begin/Release/RollbackTo).
    `n_active_writes` is incremented (asserted 0->1) when a top-level statement
    that writes begins its statement transaction (execute.rs:4521-4531) and is
    decremented in `end_statement` (mod.rs:1287-1293) which runs BEFORE the
    savepoint rollback. So while a top-level writer is suspended mid-execution
    (RETURNING row already emitted, or parked at an I/O yield) n_active_writes==1,
    and any SAVEPOINT/RELEASE/ROLLBACK TO on the same connection is rejected before
    it touches pager/savepoint state. The abort path even special-cases
    `StatementsInProgress` to NOT roll back the collided-with statement
    (mod.rs:2761). 59d03e62 is an ancestor of HEAD. The `is_nested_stmt()`
    exemption does not reopen the finding's scenario (top-level ROLLBACK TO during
    a suspended top-level writer is still caught); savepoint verbs are not emitted
    inside nested/trigger programs.
- repro-transcript: |
    # Confirmed the guard does not false-fire on normal sequential use
    # (SAVEPOINT/ROLLBACK TO/RELEASE all succeed when no writer is active — see A17-1
    # transcript). The true-positive requires partial-stepping a writer then issuing
    # a savepoint op on the same connection, which is not expressible via the CLI.

## VERDICT [A18-1] Savepoint rollback aborts partway (after WAL rewind) when a rolled-back page is pinned by a parked cursor, leaving stale pages served from cache
- verdict: REFUTED
- severity: low (the order-of-operations code pattern is real but the data-corruption trigger is unreachable)
- repro: attempted-no-repro (the reachable abort path with pinned cursors + heavy spilling produces correct rolled-back results matching SQLite)
- reasoning: >
    The order-of-operations code IS as described: `rollback_to_snapshot`
    (pager.rs:2299-2316) calls `wal.rollback(...)` then
    `delete_clean_pages_after_wal_frame(...)?` (which propagates
    `CacheError::Pinned`/`Locked` from `_delete`, page_cache.rs:337-351) BEFORE
    `invalidate_all_cursors()`. But the triggering precondition — a clean page with
    `wal_tag > target` that is PINNED and present in the cache MAP at the delete
    step — is not reachable:
    (1) Every page with `wal_tag > target` that is `<= savepoint.db_size` was
    necessarily written to a WAL frame > target within the rolled-back range, and
    the SPILL path itself calls `subjournal_page_if_required` before appending to
    WAL (pager.rs:3980), so such a page is always subjournaled under the newest
    savepoint. The rollback loop then restores it via `force_upsert_page_in_cache`,
    which REPLACES the map entry in place (upsert_page -> _insert update_in_place,
    page_cache.rs:281) with a DIRTY pre-image and clears its wal_tag
    (pager.rs:5704-5705). That removes any pinned clean re-read copy from the map;
    the restored page is dirty (excluded by `delete_clean_pages`'s
    `!is_dirty() && has_wal_tag()` filter).
    (2) Pages with id `> db_size` are removed by `cache.truncate(db_size)`
    (pager.rs:2294) which runs BEFORE `wal.rollback`; a pinned one would bail THERE
    (before the WAL is rewound), which is not the finding's "after rewind" outcome.
    (3) RELEASE extends the parent's subjournal write_offset to cover the released
    child's range (pager.rs:2084-2085), so released-savepoint pages are still
    replayed on rollback to the parent — no clean survivors from that path either.
    Empirically confirmed: the exact abort scenario (mid-statement UNIQUE violation
    while the aborting statement's own btree cursors are alive/pinned — vtab cursors
    only are closed at mod.rs:2649 — with cache_size=2 forcing spills, reading
    BEFORE any explicit rollback) rolls back correctly and matches SQLite, ok
    integrity, across reopen; the named-savepoint ROLLBACK TO path with a released
    inner savepoint and heavy spills is likewise correct.
    Residual (NOT this finding, not confirmed): `cache.truncate` can bail on a
    pinned page > db_size BEFORE `wal.rollback` only under an exotic same-connection
    reader interleaving (a suspended SELECT, n_active_writes==0 so A17-2's guard
    does not apply, parked on a writer's newly-allocated page during a write abort).
    That is tied to the already-flagged systemic single-read-slot interleaving
    issue and could not be constructed; it is an error-path (InternalError) case,
    not the silent data corruption claimed.
- repro-transcript: |

    # read IMMEDIATELY after the constraint error with NO explicit rollback:
    $ ... BEGIN; SAVEPOINT sp;
      UPDATE t SET payload='XXXX..(4000)', u2=CASE WHEN u2=40 THEN 1 ELSE u2 END WHERE TRUE;
