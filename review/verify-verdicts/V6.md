## VERDICT [A16-1] to_sql() drops DESC and COLLATE from table-level UNIQUE constraints, corrupting the autoindex after ALTER TABLE + reopen
- verdict: CONFIRMED
- severity: critical
- repro: yes (transcript below)
- reasoning: End-to-end reproduced exactly as described. `BTreeTable::to_sql()` at core/schema.rs:3778-3785 emits only `quote_ident(&unique_column.name)` — `UniqueSetColumn` carries `sort_order` and `collation` (struct at core/schema.rs:3150-3155) but neither is emitted. ALTER TABLE ADD COLUMN rewrites the stored SQL through `to_sql()`, so `UNIQUE(a DESC, b)` -> `UNIQUE (a, b)` and `UNIQUE(a COLLATE NOCASE, b)` -> `UNIQUE (a, b)`. On reopen the schema loader rebuilds the in-memory autoindex from the parsed constraint's `sort_order` (core/schema.rs:1891-1892) — now ASC/BINARY — while the physical autoindex b-tree keeps its original DESC/NOCASE ordering. The mismatch is real data corruption: the duplicate INSERT is silently accepted (UNIQUE violated), an equality lookup misses the pre-existing row (silent wrong result), and PRAGMA integrity_check reports "row N missing from index" / "non-unique entry in index". SQLite 3.45.1 oracle preserves DESC/COLLATE after ALTER (it appends the column instead of re-rendering), rejects the duplicate, and integrity_check is "ok" — so this is a clean Turso-vs-SQLite divergence. Note the DESC case has integrity_check fail; the NOCASE case only fails integrity_check when the stored values' NOCASE and BINARY orderings actually diverge (e.g. 'a' vs 'B'); with all-lowercase values ('abc'/'def') the two orders coincide so integrity_check says "ok" even though the duplicate is still wrongly accepted. The finding's blanket "integrity_check fails" for NOCASE is therefore slightly value-dependent, but the core defect (dropped attribute + accepted duplicate + corruptible index) holds fully. This turns a former loud reopen panic into silent corruption, violating the project's crash>corrupt rule.
- repro-transcript: |

    CREATE TABLE t (a INTEGER, b TEXT, c INT, UNIQUE (a, b))      # DESC dropped
    # --- invocation 2 on SAME t1.db (reopen) ---

## VERDICT [A16-3] Locale collation ids stored in a 12-bit field but registry allows 65k ids — silent collation truncation via `& COLL_MASK`
- verdict: CONFIRMED (code defect provable by reading; trigger impractical)
- severity: low (was rated medium; downgraded — requires 4092 distinct ICU locale collations registered in one long-lived process, which is not realistically reachable, and never in a test)
- repro: not-attempted (needs 4092 distinct valid ICU locale collations registered in a single process; impractical, as the finding itself states)
- reasoning: The defect is a deterministic consequence of the constants, verified by reading. Column collation is packed into a 12-bit field: COLL_SHIFT=8, `COLL_MASK = 0b1111_1111_1111 << 8` (core/schema.rs:5240-5241) — max storable value 4095. Both store sites mask with `& COLL_MASK` and silently drop high bits (core/schema.rs:5339 in `Column::new`, 5407 in `set_collation`). The stored token is `CollationSeq::to_bits()`, which for `Locale(id)` is `registry_index + 4` (collate.rs:80, 245-247). The guard that should reject overflow, `LocaleCollationId::from_index`, only errors when `index > u16::MAX - 4` = 65531 (collate.rs:232-238) — far above the 12-bit boundary — so the error never fires at index ~4091. Read-back `Column::collation()` maps a truncated 0 back to Unset->Binary (core/schema.rs:5388-5395) with nothing detecting the mismatch. Arithmetic (verified): registry index 4091 still fits (Locale 4091); index 4092 -> to_bits 4096 -> masks to 0 -> read as Binary; 4093 -> Binary; 4094 -> NoCase; 4095 -> Rtrim; 4096 -> wraps to Locale(index 0). A column declared with a locale collation past the boundary then compares/orders/indexes under the WRONG collation silently — same seek-order corruption class as A16-1 if it backs an index. The finding's exact per-index labels are off by one in spots (it says the 4094th wraps to NoCase; actually index 4094 -> NoCase, index 4093 -> Binary) but the mechanism and the 4092-collation threshold are correct.
- repro-transcript: |
    # bit-layout arithmetic (COLL_SHIFT=8, COLL_MASK=0xFFF<<8):
    idx=4091 to_bits=4095 -> stored v=4095 => Locale(idx=4091)   # last that fits
    idx=4092 to_bits=4096 -> stored v=0    => Unset->Binary        # silent truncation
    idx=4093 to_bits=4097 -> stored v=1    => Binary
    idx=4094 to_bits=4098 -> stored v=2    => NoCase                # wrong collation
    idx=4095 to_bits=4099 -> stored v=3    => Rtrim
    idx=4096 to_bits=4100 -> stored v=4    => Locale(idx=0)         # wraps to different locale
    from_index cap rejects idx > 65531, NOT 4091  -> no error at the 12-bit boundary

## VERDICT [A16-4] generate_series with a literal NULL stop scans 4,294,967,295 rows instead of returning empty
- verdict: CONFIRMED
- severity: medium
- repro: yes (transcript below)
- reasoning: Reproduced. `SELECT * FROM generate_series(1, NULL)` did not finish within a 15s timeout in the debug build (exit 124). EXPLAIN matches the finding almost verbatim: `VFilter 0 9 1` receives only the start arg (r[3]='1'), then `VColumn 0 2 4` reads the hidden stop column and `NotNull 4 8` post-filters, looping via `VNext 0 4` over the full series. In `filter()` (core/series.rs:166-199), because the stop constraint never reaches VFilter (idx_num & 2 == 0), the `else` branch sets `stop = DEFAULT_STOP_OMITTED = Some(u32::MAX as i64)` = 4294967295 (series.rs:171,184), so the entire 1..4.29e9 series is instantiated and every row is rejected by the post-filter. The distinct runtime-NULL path proves the divergence is specific to the planner-dropped literal NULL: `generate_series(1,(SELECT 5 WHERE 0))` returns 0 rows instantly via the `stop.is_none() -> EOF` branch (series.rs:197-199). No sqlite3 binary is installed here for a direct oracle, but SQLite's series.c returns an empty series when any argument is NULL, and series.rs:198's own comment ("Sqlite returns an empty series for wacky args") confirms the intended-equivalent behavior — so a legitimate query that is instant in SQLite hangs on billions of iterations in Turso (multi-minute even in release). Medium is fair: eventually-correct (0 rows) but an effective DoS on a trivial query.
- repro-transcript: |
    $ printf 'SELECT * FROM generate_series(1, NULL);' | timeout 15 tursodb -q :memory:
    exit code: 124        # timed out / hang (debug build iterating ~4.29B rows)

    $ printf 'EXPLAIN SELECT * FROM generate_series(1, NULL);' | tursodb -q :memory:

    3|VFilter|0|9|1||0|                 # only 1 arg (start); stop NOT passed
    4|VColumn|0|2|4||0|                 # reads hidden stop column
    5|NotNull|4|8|0||0|r[4]!=NULL -> goto 8   # per-row post-filter
    7|ResultRow|1|1|0||0|
    8|VNext|0|4|0||0|                   # loops over the whole series

    $ printf 'SELECT * FROM generate_series(1,(SELECT 5 WHERE 0));' | timeout 15 tursodb -q :memory:
    (0 rows, instant, exit 0)          # runtime NULL -> stop.is_none() -> EOF branch
