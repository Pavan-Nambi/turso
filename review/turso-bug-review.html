Start here — the six that matter most

  1. OFFSET over a nested-loop join silently drops rows (new) — pagination over joins is broken.
  2. Comparison collation ignores the left operand's column (new) — bincol = nocasecol uses NOCASE everywhere.
  3. jsonb_set corrupts nested-array documents — an ordinary UPDATE can persist unreadable JSONB.
  4. ALTER TABLE drops DESC/COLLATE from UNIQUE — autoindex corruption after reopen.
  5. Partial index drops rows from a LEFT JOIN's preserved side.
  6. GROUP BY sorter elided on a hash-join build side (new) — split groups, wrong counts.

C1CriticalNew
OFFSET over a nested-loop join skips offset × (product of inner sizes) rows
at-head presentroot core/translate/main_loop/body.rs:419class sql-semantics

The OFFSET jump target uses join_order.first() (the outermost loop) where it must use the innermost, so a positive OFFSET consumes whole outer-loop iterations. Masked by ORDER BY, hash joins, and single-table queries — which is why it went unnoticed. Breaks the common "paginate over a join" pattern.

a=(1,2) · b=(10,20)
SELECT x,y FROM a,b LIMIT 3 OFFSET 2;
  turso   (0 rows)            # silently drops everything
  sqlite  (2,10), (2,20)
C2CriticalNew
Comparison collation ignores the left operand's column collation
at-head presentroot core/schema.rs:5379 · translate/expr/binary.rs:449class sql-semantics

Column::collation_opt() returns None for a default-BINARY column, so a column with implicit BINARY collation reports "no collation" and resolution falls through to the other operand's explicit collation — violating SQLite's "left operand column wins" rule (quoted verbatim in turso's own doc comment). Affects WHERE, ON, and every join type, not just hash joins. Case-insensitive columns compared to plain columns silently match wrong rows.

tb.b TEXT (binary) · tn.n TEXT COLLATE NOCASE · tb=('abc','ABC') · tn=('abc')
SELECT tb.b FROM tb, tn WHERE tb.b = tn.n;
  turso   abc, ABC   # used NOCASE
  sqlite  abc        # left operand is BINARY
# LEFT JOIN drops the null-padded row; control (tn.n = tb.b) agrees on both
C3Critical
json_set/jsonb_set double-adds size delta on consecutive-array paths
at-head presentcommit 1fa653b8 (2026-02-27)root core/json/jsonb.rs:2539

For a path with two or more adjacent array locators ($[i][j][k]), a shared header is rewritten twice, so the stored element size is wrong by delta. Manifests as a runtime error, a swallowed SQL NULL, or a silently corrupted blob that later reads back as malformed — durable data loss through an ordinary UPDATE.

jsonb byte-level
SELECT hex(jsonb_set('[[[1]]]','$[0][0][0]','short'));
  turso   8B BB 6B…   # BB = size 11, real content 7
  sqlite  8B 7B 6B…
UPDATE t SET j=jsonb_set(j,'$.geometry.coordinates[0][0][0]',99.5);
  then SELECT json(j) → "malformed JSON"  # document destroyed
C4Critical
to_sql() drops DESC/COLLATE from UNIQUE → autoindex corruption after ALTER + reopen
at-head presentcommit e4785093 (2026-02-26)root core/schema.rs:3778

Any ALTER TABLE ADD/DROP/RENAME COLUMN rewrites the stored SQL, turning UNIQUE(a DESC,b) into UNIQUE(a,b). On reopen, the in-memory index claims ASC/BINARY while the on-disk b-tree was written DESC/NOCASE. Replaced a loud reopen crash with silent corruption — violating the project's own "crash > corrupt" rule.

after ALTER TABLE t ADD COLUMN c; reopen
INSERT INTO t(a,b) VALUES (1,'x');   # accepted — duplicate of existing row
SELECT * FROM t WHERE a=1 AND b='x'; # returns 1 row, two exist
PRAGMA integrity_check;              # "row missing from index / non-unique entry"
C5Critical
Partial index on the preserved side of an OUTER JOIN silently drops rows
at-head presentcommit 9cbc321d (2026-04-30)root core/translate/optimizer/constraints.rs:1470

can_use_query_term early-returns true when the table has no join_info — exactly the case for the preserved left table. A partial index whose predicate matches an ON term then drives the scan, skipping the left rows a LEFT JOIN must still emit null-padded.

CREATE INDEX partial_t ON t(a) WHERE b>0
SELECT t.a,t.b FROM t LEFT JOIN s ON t.b>0 ORDER BY t.a;
  turso   (2,3), (4,10)                  # b<=0 rows dropped
  sqlite  (1,-5), (2,3), (3,-1), (4,10)  # t is preserved

H1HighNew
GROUP BY / ORDER BY sorter wrongly elided on a hash-join build side
at-head presentroot core/translate/optimizer/order.rs (plan_satisfies_order_target)

The sorter is dropped when GROUP BY/ORDER BY can be served from a build-side index scan — but the hash-join output is ordered by the probe side, so streaming aggregation splits a group into partial counts. Guarded for LEFT/FULL outer joins, not for inner ones. HAVING count(*)>1 then silently returns nothing.

t1 JOIN t2 ON t2.a=t1.a
SELECT t1.b,count(*) FROM t1 JOIN t2 ON t2.a=t1.a WHERE t1.c>=0 GROUP BY t1.b;
  turso   0|1, 1|1, 0|1, 1|1   # groups split
  sqlite  0|2, 1|2
H2HighNew
Outer OR IGNORE leaks through a DELETE-trigger boundary and swallows a conflict
at-head presentroot core/translate/trigger_exec.rs:678 (ignore_jump_target)

The a48e3f01 fix reset only the compile-time conflict override. An outer OR IGNORE still propagates at runtime, so a conflict inside a fired DELETE trigger's body jumps to the outer ignore target instead of aborting — even an explicit inner INSERT OR ABORT is overridden.

AFTER UPDATE trigger deletes from t2; BEFORE DELETE on t2 inserts a PK-conflicting row
UPDATE OR IGNORE t SET x=9;
  turso   no error, t=(1,9) applied   # conflict swallowed
  sqlite  aborts: UNIQUE constraint failed: t2.pk
H3High
repeat()/lpad()/rpad() allocate an attacker-controlled length with no cap
at-head presentcommit c681ded5 (2026-06-17)root core/functions/string.rs:31

Uses the infallible allocator with no MAX_BLOB_LENGTH/TooBig guard (unlike zeroblob/randomblob). With panic="abort" (release/fuzzing profiles) it hard-aborts the embedding process — a one-statement DoS.

count taken straight from SQL (up to i64::MAX)
SELECT repeat('ab', 9223372036854775807);  # panic "capacity overflow" (exit 101)
SELECT lpad('x', 9223372036854775807);     # handle_alloc_error → SIGABRT (exit 134)
H4High
JSONB $[#] / append-by-index leaves the container header one byte short
at-head presentcommit fc0e5241 (2026-06-24)root core/json/jsonb.rs:372

The immediate container header is updated with delta only; the spliced placeholder byte is forwarded to ancestors but not to the container itself. The result is a JSONB blob whose declared size disagrees with its length — turso cannot read back its own output.

append to array
SELECT hex(jsonb_set('[1,2,3]','$[#]',4));   turso 7B… (size 7, actual 8) · sqlite 8B…
SELECT json(jsonb_set('[1,2,3]','$[#]',4));  turso Parse error
H5High
Use-after-free in the cursor registry: raw pointers parked across IO yields
at-head presentcommit f63bd46f (2026-06-04)root core/storage/btree.rs:6081

drive_pending_peer_save snapshots raw NonNull<dyn CursorTrait> pointers then yields on an overflow-page read. Nothing scrubs a peer's snapshot when that peer statement is reset/dropped (which frees the cursor box). On resume the writer dereferences freed memory — a sequential (non-concurrent) UAF reachable from normal binding/GC usage. Verifier could not refute.

H6High

at-head presentcommit 98b46b15 (2026-02-24)root core/translate/expr/condition.rs:63

The NULL tracker is built from tuple component 0 only, so a NULL in a later component is invisible to three-valued logic and IN wrongly resolves to FALSE.

3-valued logic on row values

SELECT (1,NULL) NOT IN ((1,2));  turso 1   · sqlite NULL

M1Medium
HAVING aliased-aggregate check rejects valid SQL when a real column shares the alias name
at-head presentroot core/translate/select.rs:1934

The check ignores that real table columns outrank result-column aliases in SQLite name resolution. SELECT count(*) AS c, a FROM t GROUP BY a HAVING max(c)>0 (with a real column c) → turso "misuse of aliased aggregate c"; sqlite returns rows.

M2Medium

at-head presentroot core/connection.rs (set_check_constraints_ignored)

The setter omits bump_prepare_context_generation(), so a cached statement keeps its compile-time CHECK decision after the pragma flips — a cached INSERT can silently bypass CHECK. Reachable via prepare_cached.

M3MediumNew
Valid FULL OUTER JOIN … ON a=b rejected when the right table indexes the join column
at-head presentroot core/translate/…/join.rs:427,634

rhs_has_selective_seek disables the hash join; FULL OUTER has no nested-loop fallback, so no plan is found. Since indexing a join key is ubiquitous, common FULL OUTER JOINs fail with the misleading "requires an equality condition" — even though the ON clause is equality.

M4MediumNew
Outer OR ABORT fails to override a trigger body's own conflict clause
at-head presentroot core/translate/insert.rs:596 · emitter/update.rs:610

The override test uses the collapsed on_conflict != Abort, which cannot distinguish explicit OR ABORT (must override the body) from a plain statement (defers to the body). A trigger body's OR IGNORE/OR REPLACE wrongly stays in effect. The correct signal already exists but isn't used here.

M5MediumNew
sqlite3_value_blob UAF fix is incomplete — now NULL-derefs on TEXT values
at-head presentcommit c425580aroot bindings/c/src/lib.rs

The fix stopped the BLOB use-after-free but dropped Text→bytes coercion, so value_blob(text) returns NULL while value_bytes(text) returns the length. The standard memcpy(dst, value_blob(v), value_bytes(v)) idiom NULL-derefs on a text argument. Traded a UAF for a NULL-deref.

M6MediumNew
Parser MAX_EXPR_DEPTH = 100 rejects valid expressions SQLite accepts (limit is 1000)
at-head presentcommit 18ba9c9c

A 100-term OR chain SQLite runs is rejected with "Expression tree is too large" (boundary 99 pass / 100 fail). Reject-over-crash is fine; the threshold is 10× too aggressive and bites machine-generated queries.

M7Medium

at-head presentcommit b1bf20df (2026-05-11)root core/io/mod.rs:460

The default file_id calls std::fs::metadata; a custom/object-store VFS whose paths don't exist on the host FS never registers → two independent Database/WalFileShared over the same storage → lost dedup, no OS locks → WAL corruption risk.

Refuted & tested-clean

what did not survive verification, and where the engine held up

Refuted (1) — A18-1 savepoint rollback aborts on a pinned page. The order-of-operations pattern is real, but the trigger is unreachable: the spill path subjournals the page before appending to the WAL, so any clean page newer than the rollback target is restored dirty (which clears its wal_tag) and is excluded from the failing delete. Empirically, mid-statement abort with heavy spilling and pinned cursors produced correct results matching SQLite.

Tested clean (negative results worth recording):

  • Multi-index OR / access-path union — ~24,000 differential queries (branches, ranges, dedup, IS NULL seeks, partial indexes, NOCASE, DML incl. Halloween, 20k-row RowSet dedup). The 5025064b unify-access-paths refactor is solid.
  • Aggregate FILTER clause — ~20,000 fuzz + 130 hand cases with GROUP BY / DISTINCT / subqueries / HAVING — all match SQLite.
  • vdbe execution core (A40–A43, ~80 commits) — REAL-affinity coercion, RENAME COLUMN expr-index rewrite, BEGIN CONCURRENT guard, REINDEX, Step-yield, log/log2/log10 bit-for-bit, aggregate-arg collation, EXPLAIN panic fix.
  • Hash-join cross-product multiplicity and FULL OUTER null-extension — ~7,000 fuzz queries, no divergence beyond C2 and M3.

Method. Each of the paused session's 35 findings was re-checked by an independent adversarial verifier (default-refute; read code at HEAD + callers; check for later fixes; live repro against the SQLite 3.45.1 oracle). New findings came from differential fuzzing on the flagged behavior classes plus fresh review of never-started batches (vdbe, bindings-FFI). All critical/high findings were re-reproduced by hand.

Coverage still open for a follow-up: remaining killed translate batches (A21–A39), other bindings (A00–A07), sync durability (A45), cli/packaging/serverless-JS (B46–B49), and the 93 test-only commits (skim for masked regressions). Joins, collation, JSON, schema/DDL and conflict-resolution were the productive veins; vdbe / OR / FILTER tested low-yield.
