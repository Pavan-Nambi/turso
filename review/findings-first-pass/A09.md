## [A09-1] External aggregate called with wrong arg count now reports "no such function" instead of "wrong number of arguments"
- commit: 2cbc2d13fd267fc26c69351004eeda408a269d06 "Add managed aggregate callback support" (2026-05-27)
- file: core/function.rs:110 (root); observable at core/connection.rs:5111
- at-head: present
- category: sql-semantics
- severity: low
- confidence: high
- description: The commit changed `ExtFunc::matches_arg_count` for the `Aggregate` arm from unconditionally `true` to `*argc < 0 || *argc as usize == arg_count`. `SymbolTable::resolve_function` filters candidates through `matches_arg_count`, so a fixed-arity external aggregate invoked with the wrong number of arguments no longer resolves at all, and the caller falls through to the generic "no such function" error. Before this commit the function resolved (aggregates matched any arity), then `translate_aggregation_step` bailed with "External aggregate function called with wrong number of arguments". Both real SQLite and turso's prior behavior report a wrong-argument-count error; the new message wrongly claims the function does not exist. Valid-arity calls are unaffected (verified: `median(x)`, `first_value`/`last_value`, `dense_rank` all correct), and variadic aggregates (`argc < 0`) still match any count, so this is purely an error-message regression on a misuse path.
- failure: `SELECT median(1,2);` or `SELECT percentile(1);` → `Parse error: no such function: median` / `no such function: percentile`, even though both aggregates are registered (percentile feature is on by default). SQLite and pre-commit turso report a wrong-number-of-arguments error instead. Misleading diagnostic for a user who mistyped the arity of an existing function.
- evidence: |
    core/function.rs:107-111 at HEAD:
      pub fn matches_arg_count(&self, arg_count: usize) -> bool {
          match self {
              Self::Scalar { argc, .. } => *argc < 0 || *argc as usize == arg_count,
              Self::Aggregate { argc, .. } => *argc < 0 || *argc as usize == arg_count,  // was `Self::Aggregate { .. } => true`
          }
      }
    core/connection.rs:5098-5112 — resolve_function returns None when the filter rejects, so name resolution treats the aggregate as absent.
    Reproduced against the HEAD debug binary: `SELECT median(1,2)` → "no such function: median"; `SELECT median(x) FROM t` (correct arity) works and returns the median.

## Batch summary
- reviewed: 20 commits (0 skipped as excluded-only; passive-checkpoint 0bed079 and MVCC-reprepare 9a218ef were reviewed only for their shared/stable-path hunks per the batch notes)
- notable-but-not-findings / hunches:
  - **Managed-aggregate FFI context lifetime (2cbc2d13).** `ExtFunc::with_aggregate_arg_count` (core/function.rs:118) clones a variadic aggregate's `ExtFunc` into a fresh `Arc` stored in the compiled program, copying the `context: usize` pointer but setting `context_destructor: None`. The original (in the connection symbol table) keeps the destructor. Correct for double-free avoidance, but if the symbol-table entry is dropped (extension unload / connection teardown) while a prepared statement still holds the clone, the clone's `context`/callback pointers dangle → potential use-after-free on next execution. Pre-existing FFI-lifetime pattern, not clearly reachable from safe SQL, but worth a second look by verifiers.
  - **WAL orphan-discard aggressiveness (16c15e5).** `Database::header_validation` discards a WAL when `max_frame > 0 && db_file.size() == 0` (core/database.rs:2096). Verified against stock SQLite that WAL-mode writes page 1 to the main file immediately, so a 0-byte main file + populated WAL is genuinely orphaned and SQLite discards it too — no data loss for images produced by the new fsync path. Databases created by *older* turso builds that crashed pre-first-checkpoint with a 0-byte main file would have their committed WAL discarded, but that image was already unrecoverable/corrupt under the old code. Read-only path uses `WalFileShared::new_noop()` and never deletes; looks correct. Flagging only because it is a durability-adjacent behavior change.
  - **allocate_page1 unconditional fsync under synchronous=OFF (16c15e5).** The new `AllocatePage1State::Syncing` fsyncs page 1 to the main file whenever `self.wal.is_some()`, even with `synchronous=OFF` (vacuum tests updated from `before.db==0` to `==1` to match). Intentional per the PR, but it is a real change for anyone relying on synchronous=OFF meaning zero db-file fsyncs.
  - **refresh_schema_from_shared_for_reprepare now bumps prepare-context generation (9a218ef).** The consolidated reprepare helper (core/connection.rs) calls `bump_prepare_context_generation()` on refresh, which the old inline statement.rs block did not. Non-MVCC version-comparison branch is otherwise identical; the extra bump can cause additional (harmless) repreparation of sibling statements, not incorrectness. No loop risk since the reprepared statement is compiled at the current generation.
