## [A12-1] JSONB parent-size bookkeeping double-adds delta for consecutive array ancestors — errors and silent persisted corruption on nested-array paths
- commit: 23c1500622473d26c615203d1e5ee1075bb622cd "Merge 'Fixes various json compatibility issues' from" (2026-02-27) — inner commit 1fa653b8b120055fcb10513f591c75a44b6c3e81 "fix json insert"
- file: /home/user/turso/core/json/jsonb.rs:2533-2574 (update_parent_references; double-add at 2543-2558)
- at-head: present
- category: data-corruption
- severity: critical
- confidence: high
- description: The commit removed the `is_prev_arr` guard from `update_parent_references`. When the traversal stack contains two adjacent entries that are both arrays (path has >= 2 consecutive array locators that are not the path tail, e.g. `$[i][j][k]` or `$[i][j].k`), entry k's `field_value_index` header is the same header as entry k-1's `array_index`. The loop now updates that shared header twice: once as level k's own container header (correct total) and again as level k-1's "array element" header with `arr_el_size + delta` added a second time. The stored element size becomes wrong by `delta`. Before the commit the `is_prev_arr` flag skipped exactly this second update for consecutive arrays (the removal fixed a different case, `$[i].a[j][k]`-style, but broke the adjacent-array case). Depending on the entry function, the result is a runtime error on valid SQL, a silent NULL, or a silently corrupted JSONB blob that gets persisted.
- failure: |
    All against HEAD build; real SQLite (3.45.1) returns correct results for every one of these.
    - `SELECT json_set('[[[1]]]','$[0][0][0]','short');` → `Runtime error: Parse error: Failed to read header byte` (any replacement whose size differs from the old value; same for `$[0][0].a` shapes, e.g. `json_set('[[{"a":1}]]','$[0][0].a','longvaluehere')`).
    - `SELECT json_insert('[[[1]]]','$[0][0][1]',2);` → SQL NULL (silently; SQLite: `[[[1,2]]]`), because ops.rs swallows the internal error via `let _ = json.operate_on_path(...)`.
    - `SELECT hex(jsonb_set('[[[1]]]','$[0][0][0]','short'));` → `8BBB6B5773686F7274` with **no error**: middle array header `BB` claims size 11, actual content is 7 (correct blob is `8B7B6B...`). `SELECT hex(jsonb_remove('[[[1,2]]]','$[0][0][1]'));` → `4B1B2B1331` (middle header size 1, should be 3, correct is `4B3B2B1331`).
    - End-to-end silent data loss with a realistic GeoJSON shape:
      `CREATE TABLE t(id INTEGER PRIMARY KEY, j BLOB); INSERT INTO t VALUES (1, jsonb('{"geometry":{"coordinates":[[[1,2],[3,4]]]}}')); UPDATE t SET j = jsonb_set(j, '$.geometry.coordinates[0][0][0]', 99.5);` succeeds, then `SELECT json(j) FROM t;` → `Runtime error: Parse error: malformed JSON`. The stored document is destroyed.
- evidence: |
    core/json/jsonb.rs:2539-2558 (HEAD):
        for parent in stack.iter().rev() {
            let (JsonbHeader(el_type, el_size), el_header_len) = self.read_header(parent.field_value_index)?;
            if el_type == ElementType::ARRAY {
                let arr_element_idx = parent.get_array_index()...;
                ...
                let new_arr_el_header_len = self.write_element_header(
                    arr_element_idx, arr_el_type, (arr_el_size as isize + delta) as usize, true)?;
    For consecutive array stack entries, `parent.get_array_index()` of the outer entry equals `field_value_index` of the inner entry, whose header was already rewritten (with delta included) on the previous loop iteration as its own container header; the outer iteration then adds `delta` to the already-updated size. The removed guard (diff of 1fa653b8): `if el_type == ElementType::ARRAY && !is_prev_arr { ... is_prev_arr = true } else { is_prev_arr = false }` skipped exactly this second write when the leaf-ward parent was also an array. Trace for `json_set('[[[1]]]','$[0][0][0]','short')` (delta=+4): middle array header correctly becomes 7 as own header, then outer iteration rewrites it to 7+4=11 → observed `BB` byte in the jsonb_set output.

## [A12-2] JSON-null early return in json_string_to_db_type hijacks String/Binary output variants — json_set/jsonb_set family returns SQL NULL for top-level JSON null documents
- commit: eed5c44f64d1f31e38ee49664590d5ab7ad102da "Merge 'core: Adapt null handling in json_string_to_db_type' from Patrick Pichler" (2026-03-19)
- file: /home/user/turso/core/json/mod.rs:619-621
- at-head: present
- category: sql-semantics
- severity: medium
- confidence: high
- description: To fix `json_set(NULL, '$.a', 1)` returning the string 'null', the commit added `if element_type == ElementType::NULL { return Ok(Value::Null); }` at the very top of `json_string_to_db_type` — before the `OutputVariant::Binary` and `OutputVariant::String` handling. Previously a JSON null element under the String variant returned the text `null` and under Binary returned the JSONB blob `X'00'`. Now every function that serializes its result through the String or Binary variant returns SQL NULL whenever the document's top-level element is JSON null, diverging from SQLite and from turso's own `json()`/`->` handling of the same value.
- failure: |
    All verified at HEAD vs SQLite 3.45.1:
    - `SELECT json_set('null','$.a',1);` turso: SQL NULL; SQLite: text `'null'`. Same for `json_replace('null','$.a',1)`, `json_insert('null','$.a',1)`, `json_remove('null','$.a')`, `json_patch('{}',' null')` (whitespace defeats the exact-match shortcut of A12-3).
    - `SELECT hex(jsonb_set('null','$.a',1));` turso: NULL; SQLite: `00`. Same for `jsonb_replace`, `jsonb_insert`, `jsonb_patch('null','null')`.
    - Data-loss shape: `UPDATE t SET doc = json_set(doc, '$.flag', 1);` silently replaces every row whose doc is the valid JSON document `null` with SQL NULL.
- evidence: |
    core/json/mod.rs:619-628 (HEAD):

    Before the commit, `ElementType::NULL => Ok(Value::Null)` lived inside the match *after* the Binary/String early returns, so only the ElementType variant (json_extract-style, where SQL NULL is correct) mapped JSON null to SQL NULL. The commit moved the check above both early returns.

## [A12-4] Array-append navigation drops the placeholder delta from the immediate container header — jsonb_set/jsonb_insert with `$[#]` (and append-at-end index) return invalid JSONB
- commit: fc0e5241a425306730288b7bf99b57db853ad64b "Merge 'json: fix json_set panics on array append' from Artur Kantorczyk" (2026-06-24)
- file: /home/user/turso/core/json/jsonb.rs:2660,2853 (None append arms), 372-384 (SetOperation::execute container update)
- at-head: present
- category: data-corruption
- severity: high
- confidence: high
- description: The commit added handling for the `$[#]` append locator (previously `unreachable!()` panic): it splices a 1-byte placeholder at the end of the array and records that byte in `JsonTraversalResult.delta` (`target.delta`). But `SetOperation::execute` (and the Replace/Insert/Delete twins) updates the immediate container's header with only `delta` (new value size minus placeholder size) — `target.delta` is only forwarded to *outer* ancestors via `update_parent_references(stack, target.delta + delta + h_delta)`. The appended-to array's size header therefore ends up short by exactly the placeholder byte. Text-mode `json_set` masks this (its serializer doesn't trust the root size), so the commit's own tests pass, but the Binary variant (`jsonb_set`/`jsonb_insert`) returns the raw bytes: a JSONB blob whose declared size disagrees with its length. Turso's own `json()` then rejects the blob. The pre-existing `Some(idx)` append-at-end path (e.g. `$[1]` on a one-element array) exhibits the same short-by-one header at HEAD (its lineage runs through 23c15006's navigation rewrite), so this finding covers both arms; the `$[#]` arm is the one this commit introduced (panic → silent corruption).
- failure: |
    At HEAD (SQLite 3.45.1 correct in all cases):
    - `SELECT hex(jsonb_set('[1,2,3]','$[#]',4));` → `7B1331133213321334`-family: `7B` root header claims payload 7, actual 8. SQLite: `8B1331133213331334`. No error is raised.

    - Nested: `SELECT hex(jsonb_set('{"a":[1]}','$.a[#]',2));` → `7C17613B13311332`: inner array header `3B` (size 3) should be `4B`; `json()` of it → parse error.

## [A12-5] Bracket-quoted JSON path on an array node returns NULL where SQLite raises "bad JSON path"

- file: /home/user/turso/core/json/path.rs:338; /home/user/turso/core/json/jsonb.rs:3064-3067
- at-head: present
- category: sql-semantics
- severity: low
- confidence: high
- description: The commit makes `$["key"]` parse into a `BracketQuotedKey` element that never matches, on the theory that "SQLite returns NULL for bracket-notation". That is only true when the addressed node is an object; when the node is an array, real SQLite raises an error ("bad JSON path"), because a quoted token is not a valid array index. - failure: `SELECT json_extract('[1,2]','$["0"]');` → SQLite 3.45.1: error `bad JSON path: '$["0"]'`; turso: NULL. An application depending on the error to detect a bad path silently gets NULL rows instead.
- evidence: |

    core/json/jsonb.rs:3064-3067: the `_ =>` arm (`// BracketQuotedKey: SQLite compat — never matches, falls through to "Not found" → NULL`) applies regardless of the node type, so the array case cannot error.
