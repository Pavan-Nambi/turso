# Batch A18 findings — core/storage (btree, pager, WAL, page_cache)

## [A18-1] Savepoint rollback aborts partway (after WAL rewind) when a rolled-back page is pinned by a parked cursor, leaving stale pages served from cache
- commit: 3096c65e9b1990bcc7190cd6843f88be04485326 "Merge 'Add savepoint rollback DST coverage and fix rollback cache invalidation' from Yassine Elyaakoub" (2026-04-30)
- file: /home/user/turso/core/storage/pager.rs:2305-2313 (call site) and /home/user/turso/core/storage/page_cache.rs:751-771 (`delete_clean_pages_after_wal_frame`)
- at-head: present
- category: error-handling / data-corruption
- severity: high
- confidence: medium
- description: Commit 14 of this batch added `PageCache::delete_clean_pages_after_wal_frame()`, called from `rollback_to_snapshot()` right after `wal.rollback(...)` has already rewound the WAL to the savepoint position. The helper calls `PageCache::delete(key)?` for every clean page whose `wal_tag` frame is newer than the rollback target. `PageCache::delete` (`_delete`, page_cache.rs:329) returns `Err(CacheError::Pinned)` / `Err(CacheError::Locked)` for pages that are pinned or have IO in flight — and pages sitting on any parked B-tree cursor's `PageStack` are pinned (`PageStack::_push` pins, btree.rs ~8235). The error is mapped to `InternalError` and propagated with `?`, so the rollback bails out AFTER the WAL was rewound and the subjournal truncated, but BEFORE the remaining stale clean pages are purged and BEFORE `invalidate_all_cursors()` runs. In `rollback_to_newest_savepoint` the savepoint was also already popped. Nothing downstream cleans the page cache for a statement-level rollback inside an explicit transaction, so the transaction continues with a cache entry whose content belongs to the rolled-back statement.
- failure: |
    1. `BEGIN;` then run a write statement (or `SAVEPOINT s; ...`) on a small page cache so dirty pages get spilled to the WAL (frames F0+1..F1 appended after the statement savepoint opened at F0), evicted, and later re-read from the WAL — the re-read pages are CLEAN with `wal_tag = f > F0` (wal.rs:3593 sets the tag on WAL reads).
    2. The statement (or an interleaved statement on the same connection) has a cursor parked on such a page P — P is pinned via the cursor's PageStack.
    3. The statement hits e.g. a UNIQUE constraint violation → abort path runs `end_statement(RollbackSavepoint)` → `rollback_to_newest_savepoint()` → `rollback_to_snapshot()`. Note the abort path only closes virtual-table cursors before this (vdbe/mod.rs:2649); btree cursors keep their pins.
    4. `wal.rollback(RollbackTo{frame: F0,..})` rewinds the WAL, then `delete_clean_pages_after_wal_frame(F0)` hits pinned page P → `CacheError::Pinned` → `InternalError("failed to invalidate rolled-back WAL pages")`.
    Outcome: (a) the statement rollback reports an internal error instead of completing (replacing/obscuring the user's constraint error); (b) for a Constraint error inside an explicit transaction, no full-transaction rollback follows (vdbe/mod.rs:2799ff, ABORT semantics keep the tx alive), so the tx keeps running with P still cached CLEAN containing rolled-back content and with cursors never invalidated — subsequent reads of P in that transaction return data from the aborted statement (silently wrong results; if the app then writes based on them, the wrong data is committed durably).
- evidence: |
    core/storage/pager.rs:2299-2313 (HEAD) — order of operations inside rollback_to_snapshot:
        if let (Some(wal), Some(wal_pos)) = (&self.wal, savepoint.wal_pos) {
            wal.rollback(Some(RollbackTo { ... }));            // WAL already rewound
            self.page_cache.write()
                .delete_clean_pages_after_wal_frame(wal_pos.max_frame)
                .map_err(|e| LimboError::InternalError(...))?; // bails here on Pinned/Locked
        }
        self.invalidate_all_cursors();                          // never reached on error
    core/storage/page_cache.rs:751-771 — the helper filters only on `!page.is_dirty() && page.has_wal_tag() && frame > max_frame`, then `self.delete(key)?`.
    core/storage/page_cache.rs:337-351 (_delete) — returns Err for `is_locked()`, `is_dirty()`, `is_pinned()` pages.
    core/storage/btree.rs:~8234 — `// Pin the page to prevent it from being evicted while on the stack` / `page.pin();` — parked cursors hold pins across statement steps; the abort path (core/vdbe/mod.rs:2736) runs the savepoint rollback before program cursors are dropped.
    A correct handling would skip (or defer) pinned/locked entries — SQLite's equivalent invalidation never fails — instead of aborting a rollback that has already rewound the WAL.
