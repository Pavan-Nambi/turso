## [A15-1] regexp() arity check admits 1 argument, then indexes args[1] — panic/abort from plain SQL
- commit: b756295effbcd6ee09eb8cb77772bdc33747d402 "Merge 'core/regex: Add non text data for pattern matchin in regexp' from Vartan Babayan" (2026-03-16)
- file: core/regexp.rs:14 (line in commit; at HEAD the check is `args.len() != 2`)
- at-head: fixed-by 530627efe8da43cd973e303d76fe5509aee5e7cd ("core/regexp: require exactly two arguments", 2026-07-28)
- category: error-handling
- severity: medium
- confidence: high
- description: The commit rewrote `regexp()` and added an arity guard `if !(1..=2).contains(&args.len())`, which rejects 0 and 3+ arguments but deliberately admits exactly 1 argument — and the very next lines unconditionally index `args[1]`. The function is registered through the `#[scalar]` macro, which registers with argc `-1` (variadic; macros/src/ext/scalars.rs passes `-1` to `register_scalar_function`), and `ExtFunc::matches_arg_count` treats `argc < 0` as "any count" (core/function.rs:109), so `SELECT regexp('a')` compiles and calls the shim with argc=1. `args[1]` then panics inside the generated `extern "C"` shim; a panic crossing an `extern "C"` boundary aborts the whole process. Honesty note: the pre-commit code (`match (args[0].value_type(), args[1].value_type())`) also panicked for argc 0 and 1, so this commit did not introduce the argc=1 crash — it shipped an arity check whose bound (`1..=2` instead of `2..=2`) knowingly-looking still leaves it reachable, i.e. an incomplete fix that left a process-abort live for ~4.5 months. The later fix commit's own test comment confirms reachability: "argc == 1 used to be admitted and then index args[1], aborting."
- failure: `SELECT regexp('foo');` on any build between 2026-03-16 and 2026-07-28 → bounds check passes (1 ∈ 1..=2) → `args[1]` index out of bounds → panic in `extern "C" fn regexp` → process abort (whole application using the library dies, not just the statement).
- evidence: |
    core/regexp.rs at b756295:
        if !(1..=2).contains(&args.len()) {
            return Value::error_with_message("wrong number of arguments to function regexp()".into());
        }
        let Some(pattern) = args[0].to_text_coerced() else { ... };
        let Some(haystack) = args[1].to_text_coerced() else { ... };   // argc==1 → OOB panic
    macros/src/ext/scalars.rs (registration): `(api.register_scalar_function)(api.ctx, c_name.as_ptr(), -1, ...)` — variadic.
    core/function.rs:109: `Self::Scalar { argc, .. } => *argc < 0 || *argc as usize == arg_count` — 1-arg call resolves.
    Fix 530627ef changes the guard to `args.len() != 2` and adds test `regexp_rejects_wrong_arity` covering argc 0/1/3, whose comment states argc==1 previously aborted.

## [A15-2] regexp() coerces REAL operands with Rust `f64::to_string`, diverging from SQLite text coercion ("2" vs "2.0")
- commit: b756295effbcd6ee09eb8cb77772bdc33747d402 "Merge 'core/regex: Add non text data for pattern matchin in regexp' from Vartan Babayan" (2026-03-16)
- file: extensions/core/src/types.rs:327
- at-head: present
- category: sql-semantics
- severity: low
- confidence: high
- description: The new `Value::to_text_coerced` renders Float via Rust's `f64::to_string()`, which prints whole floats without a fractional part ("2", not "2.0") and large values as "1e300" rather than SQLite's "1.0e+300". SQLite's own text coercion (sqlite3_value_text — what the canonical regexp extension in ext/misc/regexp.c operates on) and turso's own `CAST(x AS TEXT)` both render REAL 2.0 as "2.0". So REGEXP over a REAL column matches against a different string than every other text-coercion surface in the engine. The Blob arm also returns NULL for non-UTF-8 blobs, where SQLite's value_text hands the bytes through. Only `regexp()` uses `to_text_coerced` today, but it is a pub API on the extension Value type, so the wrong convention can spread.
- failure: `CREATE TABLE t(x REAL); INSERT INTO t VALUES (2.0); SELECT x REGEXP '^2\.0$' FROM t;` → 0, while `SELECT CAST(x AS TEXT) REGEXP '^2\.0$' FROM t;` → 1 in the same turso build (and a SQLite build with the canonical regexp extension returns 1 for the first query). Conversely `SELECT x REGEXP '^2$' FROM t` → 1 where SQLite-convention coercion gives 0.
- evidence: |
    extensions/core/src/types.rs:327 (HEAD):
        ValueType::Float => self.to_float().map(|f| f.to_string()),   // 2.0 -> "2"
        ValueType::Blob => self.to_blob().and_then(|b| String::from_utf8(b).ok()),  // invalid UTF-8 -> None -> NULL
    Oracle: `python3 -c "...cast(2.0 as text)"` → '2.0'; Rust `2.0f64.to_string()` → "2".
    The commit's own tests (testing/runner/turso-tests/regexp.sqltest) only use floats with fractional digits (3.14, 45.6, -1.5), so the whole-float case is not pinned.

- notable-but-not-findings / hunches:

SQLite never errors on a locking_mode value (it returns the current mode), so frameworks that issue `locking_mode=NORMAL` hard-fail — but before the commit the whole pragma was unsupported and errored anyway, so it is not a regression; documented as "Partial (EXCLUSIVE only)" in COMPAT.md. Sharp edge if the pragma is ever claimed as supported.
  - 15e2a20b (empty_result_callbacks): stock sqlite3 (without SQLITE_OMIT_DEPRECATED, e.g. 3.45) returns a row `0` for `PRAGMA empty_result_callbacks`; turso returns no row. Deliberate no-op pattern (matches LegacyFileFormat), tiny query-shape divergence.
