# Adversarial review — batch A32 (core/translate)

## [A32-1] Partial index on the preserved (left) table of an OUTER JOIN silently drops rows
- commit: 9cbc321d383b46bc2d1d9a15c3f671e767a1c172 "optimizer: Properly use partial indexes for more query plans" (2026-04-30)
- file: core/translate/optimizer/constraints.rs:1459 (`partial_index_predicate_terms`), guard at 1468-1479 (`can_use_query_term`)
- at-head: present
- category: sql-semantics
- severity: critical
- confidence: high
- description: The PR let a partial index with no column constraints drive a full scan whenever every conjunct of its WHERE clause is syntactically matched by some query WHERE term. It matches against *any* query term, including OUTER JOIN `ON` terms, without requiring that the term actually filters the indexed table's contribution to the result. For the *preserved* (left) side of a LEFT JOIN, `ON` conditions do NOT remove rows — non-matching left rows are emitted null-padded. Using a partial index whose predicate equals such an `ON` term therefore skips exactly the left rows that should still appear. The later `can_use_query_term` guard (HEAD) only inspects `table_reference.join_info`, which is `None` for the left/outer table, so the guard passes all terms through and the bug persists at HEAD.
- failure: |
    CREATE TABLE t(a,b); CREATE TABLE s(x,y);
    INSERT INTO t VALUES (1,-5),(2,3),(3,-1),(4,10);
    INSERT INTO s VALUES (100,200);
    CREATE INDEX partial_t ON t(a) WHERE b>0;
    SELECT t.a,t.b FROM t LEFT JOIN s ON t.b>0 ORDER BY t.a;
    Real SQLite returns all 4 rows [(1,-5),(2,3),(3,-1),(4,10)] (t is the preserved side).
    Turso returns only [(2,3),(4,10)] — rows with b<=0 silently dropped.
    EXPLAIN QUERY PLAN shows `SCAN t USING INDEX partial_t`.
- evidence: |
    Pre-PR (constraints.rs:870-875) always rejected an empty-refs partial index as a scan driver:
        if idx.where_clause.is_some() && c.refs.is_empty() { return false; }
    Post-PR the retain keeps it when can_use_partial_index() is true, and that check matches
    the index predicate against any query term. HEAD's guard:
        if join_info.is_outer() { return term.from_outer_join == Some(table_reference.internal_id); }
    only fires when the *indexed table itself* carries an outer join_info; the left table of
    `t LEFT JOIN s` has join_info == None, so can_use_query_term returns true and the ON term
    `t.b>0` (from_outer_join = Some(s)) is accepted. Verified end-to-end with target/debug/tursodb.
