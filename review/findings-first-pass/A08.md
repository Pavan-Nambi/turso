## [A08-1] HAVING aliased-aggregate misuse check rejects valid SQL when a real column shares the alias name
- commit: c45a498dfa0c8d1f57d90a4c8d233e4650409f5b "Merge 'Improve SQLite3 tests' from Pekka Enberg" (2026-02-26)
- file: core/translate/select.rs:1943 (check added by the commit lives at 1897-1951 at HEAD)
- at-head: present
- category: sql-semantics
- severity: medium
- confidence: high
- description: The commit adds `check_aliased_aggregate_misuse` for HAVING clauses to emulate SQLite's "misuse of aliased aggregate" error (SQLite ticket #2526). The check fires whenever a bare identifier inside an aggregate call in HAVING matches an alias of an aggregate result column. But SQLite's name resolution gives real table columns precedence over result-column aliases; only when the identifier resolves to the alias (no matching column) does SQLite raise the error. Turso's check ignores column shadowing, so it rejects queries that real SQLite executes fine.
- failure: `CREATE TABLE t(a, c); INSERT INTO t VALUES (1,5),(1,7),(2,3); SELECT count(*) AS c, a FROM t GROUP BY a HAVING max(c) > 0;` — real SQLite (verified with python3 sqlite3) resolves `c` in `max(c)` to column `t.c` and returns `[(2, 1), (1, 2)]`. tursodb at HEAD (verified with the built binary) fails with `Parse error: misuse of aliased aggregate c`. The same false positive applies to identifiers inside subqueries under an aggregate in HAVING, since `walk_expr` descends into them.
- evidence: |
    core/translate/select.rs:1938-1946 (HEAD):

            for rc in result_columns.iter() {

                        crate::bail_parse_error!("misuse of aliased aggregate {}", normalized);
                    }
    No check whether the identifier also names a column of a FROM-clause table,
    which takes precedence in SQLite's lookupName (src/resolve.c: aliases are a
    fallback after table columns). Reproduced: tursodb errors, sqlite3 returns rows.

## [A08-2] prepare() on comment/whitespace-only SQL returns an error, breaking the sqlite3_prepare_v2 "SQLITE_OK + NULL stmt" contract
- commit: 4f004b9b02a4589fcafb8da42c1f6e6234a924c4 "Merge 'Fix prepare panic on comment/whitespace-only SQL' from Kumar Ujjawal" (2026-02-18)
- file: core/connection.rs:992 (bindings/c/src/lib.rs:967-971 consume it)
- at-head: present
- category: sql-semantics
- severity: low
- confidence: high
- description: The commit replaced a panic with `LimboError::InvalidArgument("The supplied SQL string contains no statements")` when the parser yields no command. That is strictly better than the panic it fixed, but it bakes a compat divergence into the C API: per the SQLite contract (https://www.sqlite.org/c3ref/prepare.html), sqlite3_prepare_v2 on input containing no SQL returns SQLITE_OK and sets `*ppStmt` to NULL. Turso's bindings/c layer maps the InvalidArgument to SQLITE_ERROR (limbo_err_code default arm) and also leaves `*out_stmt` untouched on the error path (SQLite guarantees `*ppStmt` is NULLed).
- failure: The canonical multi-statement loop — `while (*sql) { sqlite3_prepare_v2(db, sql, -1, &stmt, &sql); if (!stmt) break; ... }` — run on `"SELECT 1; -- trailing comment"`: first prepare succeeds, tail points at `" -- trailing comment"`; the next prepare_v2 call returns SQLITE_ERROR on turso where real SQLite returns SQLITE_OK with a NULL stmt, so a correct portable program falsely reports a failure.
- evidence: |

    bindings/c/src/lib.rs:967-971 (HEAD):

## [A08-3] progress handler callback runs while sqlite3_step holds the non-reentrant handle mutex — reentrant API call deadlocks
- commit: e599b9703d6c37ee49dff185d7676c59163ac50e "Merge 'sqlite3: Implement `sqlite3_progress_handler` + `sqlite3_interrupt`' from Pedro Muniz" (2026-04-07)
- file: sqlite3/src/lib.rs (sqlite3_step, at the commit); code now lives at bindings/c/src/lib.rs:1071-1081
- at-head: fixed-by 9710f11ada58ba83f7540192b2f1224a6b1b02a7 ("bindings/c: do not hold the handle lock across sqlite3_step", 2026-08-10)
- category: concurrency
- severity: medium
- confidence: high
- description: At this commit, `sqlite3_step` acquired the handle's `std::sync::Mutex` (`db.inner.lock()`) and held it across the whole step. The commit introduces the first callback that core invokes synchronously mid-step from user code: the progress handler. Any sqlite3_* call the C callback makes on the same handle (`sqlite3_interrupt`, `sqlite3_progress_handler` to clear itself, `sqlite3_last_insert_rowid`, ...) re-locks the same non-reentrant mutex on the same thread and deadlocks (std::sync::Mutex documents deadlock/panic on recursive lock). Real SQLite only forbids the handler from *modifying* the database connection; informational calls and sqlite3_interrupt are legitimate.
- failure: C app registers `sqlite3_progress_handler(db, 100, cb, ctx)` where `cb` calls `sqlite3_interrupt(db)` to implement cancellation (instead of returning 1). On the 100th VM step of any query, the process hangs forever inside sqlite3_step: the step holds `db.inner`, the callback blocks re-acquiring it in sqlite3_interrupt. Before this commit no callback ran under the lock from within step's normal instruction loop, so the API pairing introduced here created the hazard it documents.
- evidence: |
    At e599b970, sqlite3/src/lib.rs sqlite3_step:
        let mut db_inner = db.inner.lock().unwrap();
        let res = stmt.stmt.run_one_step_blocking(|| Ok(()), || Ok(()));   // invokes progress cb
        ... Err(err) => set_db_err(&mut db_inner, err),
    and sqlite3_interrupt / sqlite3_progress_handler both do `db_ref.inner.lock()`.
    The later fix's own comment (bindings/c/src/lib.rs:1074-1080 at HEAD) confirms:
        "Do not hold the handle lock across the step. A user-defined function invoked
         mid-step may re-enter the C API on the same handle ... re-locking the
         non-reentrant mutex on the same thread deadlocks."

## [A08-4] PRAGMA ignore_check_constraints never invalidates prepared statements — stale statements silently skip (or keep enforcing) CHECK constraints
- commit: 79d7435ab2e057456577ebb6014077e216584a9a "Merge 'core: Optimize prepared statement recompilation check' from Jussi Saurio" (2026-03-08)
- file: core/connection.rs:1899 (`set_check_constraints_ignored` — no generation bump); compile-time consumer core/translate/emitter/mod.rs:2283
- at-head: present
- category: logic
- severity: medium
- confidence: medium
- description: The commit replaces the rebuilt-and-compared PrepareContext with a per-connection generation counter that every compile-affecting setter must bump, and its own comment calls the scheme "a regression landmine". `PRAGMA ignore_check_constraints` is read at translate time (the emitter skips emitting CHECK-enforcement bytecode entirely when the pragma is on) but `set_check_constraints_ignored` does not bump the generation, so flipping the pragma never triggers reprepare. Attribution caveat: the pragma was already missing from the old PrepareContext struct (gap dates to 7cb4b65a "Implement CHECK constraints"), so this commit preserved rather than created the hole — but it also removed the documented checklist tying Connection fields to PrepareContext, and the defect is live at HEAD. Real SQLite honors the pragma flip for already-prepared statements (verified with python3 sqlite3: a cached INSERT that failed `CHECK(a>0)` succeeds after `PRAGMA ignore_check_constraints=ON`).
- failure: `CREATE TABLE t(a CHECK(a > 0)); PRAGMA ignore_check_constraints=ON;` then prepare `INSERT INTO t VALUES (?)` (compiled with NO check bytecode) and keep it cached (e.g. sdk-kit prepare_cached or any long-lived Statement); later `PRAGMA ignore_check_constraints=OFF` and re-run the cached statement with `-1`: generation unchanged -> `matches_connection` returns true -> no reprepare -> the insert of a CHECK-violating row succeeds silently, violating a constraint the user re-enabled. Mirror case: a statement prepared while OFF keeps rejecting rows after ON (SQLite accepts them).
- evidence: |
    core/connection.rs:1899-1902 (HEAD):
        pub fn set_check_constraints_ignored(&self, ignore: bool) {
            self.check_constraints_pragma.store(ignore, Ordering::Release);
        }                                   // <- no bump_prepare_context_generation()
    core/translate/emitter/mod.rs:2283 (HEAD):
        if connection.check_constraints_ignored() || check_constraints.is_empty() { return; }
        // CHECK bytecode is omitted at compile time, so staleness is baked into the program
    core/vdbe/mod.rs (HEAD) matches_connection compares only database_ptr + generation.
    Oracle: python3 sqlite3 shows the cached statement honors the pragma flip
    (insert of -1 fails before ON, succeeds after ON without re-preparing SQL text).

## Batch summary
- reviewed: 20 commits (0 skipped as excluded-only; for the 5 commits marked "shared-path portion only" the core/mvcc, core/incremental and encryption.rs hunks were ignored per instructions and their shared-file hunks reviewed)
- notable-but-not-findings / hunches:
  - 56179b6 (nightly Vec specialization, `--cfg nightly` builds only): `try_extend_desugared(iter, true)` reserves the size_hint UPPER bound up front, so `v.try_extend(big_vec.iter().filter(rare))` reserves capacity for the whole source (std's Extend reserves the lower bound) — memory bloat, nightly-only. The unsafe spare-capacity writes (`SetLenOnDrop` holding `&mut Vec` while writing through an earlier `as_mut_ptr`) rely on Vec's pointer-validity blessing; worth a Miri pass.
  - 6086417: the nightly TrustedLen `Result` collection does `let _ = values.push_within_capacity(value)` — currently unreachable-error by capacity math (capacity = total items >= Ok items), but silently drops values if `trusted_len`/capacity assumptions ever weaken.
  - 79d7435: the generation scheme is only sound for same-connection PreparedProgram reuse; the only cross-connection guard is `database_ptr`. If a shared (cross-connection) statement/trigger-program cache is ever added, two connections' independent counters can be numerically equal while settings differ — the old value-compare was robust to this. Audited all mutation sites of the previously-tracked fields at the merge; all bump except the pre-existing check_constraints gap (A08-4).
  - 481ad02: `ImmutableRecord::build` now walks the cloneable values iterator three times (size pass, serial-type pass, content pass); a non-deterministic iterator would produce a corrupted record header with no assertion catching it (the old `assert_eq!(buf.capacity(), ...)` sanity check was removed because recycled buffers may be larger). Current callers are register/slice iterators, which are deterministic.
  - e599b970: progress-handler cadence uses `vm_steps % ops == 0`, so the callback fires at vm_steps==0 (statement start) and re-fires on every step() re-entry while an IO-yielding instruction hasn't advanced vm_steps — extra invocations vs SQLite's every-N-opcodes; also a `callback.read()` RwLock is held while the user callback runs (self-modification would deadlock; SQLite documents such callbacks as forbidden anyway).
  - e2f9f5a: `DatabaseOpts::with_custom_types(true)` force-sets `enable_strict`, but a later `.with_strict(false)` in the builder chain silently un-does the dependency (order-dependent builder).
  - 4f004b9/c45a498: on the sqlite3_prepare_v2 error path `*out_stmt` is never set to NULL (SQLite guarantees it is); folded into A08-2.
