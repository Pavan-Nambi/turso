# Batch A19 findings — core/storage (btree, pager, WAL, checkpointing)

## [A19-1] `pending_reads` map not cleared on rollback: stale (possibly uncommitted) page images served to later transactions
- commit: e414a54ea6acf8327f49acde80a3fb1471db9352 "Merge 'Begin to remove all blocking IO from core' from Preston Thorpe" (2026-05-28)
- file: core/storage/pager.rs:5744 (the `reset_internal_states` clear at HEAD; missing entirely at the commit — commit's `reset_internal_states` at pager.rs:5295)
- at-head: fixed-by 4b0255752510ecf4cceb0a94fb785be492a17871 (2026-07-01, "core/pager: reset pager state on savepoint rollback")
- category: data-corruption
- severity: critical
- confidence: high
- description: This commit introduced `Pager::pending_reads`, a map memoizing an in-flight `(PageRef, disk-read completion)` when `read_page` yields because the page cache is full and a spill is in flight. The entry is removed only when a later `read_page(page_idx)` call reaches `IOResult::Done`. Nothing removed entries on transaction rollback or statement abandonment: `reset_internal_states()` at this commit reset every other pager state machine but not `pending_reads`. `read_page` consults `pending_reads` BEFORE the page cache, so after a rollback (which clears the page cache and rewinds the WAL) a stale entry still short-circuits the next read of that page and hands out a `PageRef` whose buffer was filled from the pre-rollback WAL state.
- failure: Write txn on connection C modifies page P; cache pressure spills P's frame to the WAL (uncommitted). P is later evicted; the same txn reads P again → `read_page` issues a WAL-frame read of the uncommitted image, stores a `pending_reads[P]` entry, and yields on spill IO. The app drops/resets the statement instead of resuming; the txn rolls back → WAL frames rewound, page cache cleared, but `pending_reads[P]` survives. Any later transaction on the same connection reads P → `read_page` finds the stale entry, `cache_insert` succeeds, and the rolled-back (uncommitted) page image is returned as current data → wrong query results; if that page is then modified and committed, the rolled-back bytes become durable corruption.
- evidence: |
    At e414a54, `read_page` (core/storage/pager.rs ~3055):
        let pending = self.pending_reads.read().get(&page_idx).cloned();
        let (page, c_disk) = if let Some(pending) = pending { (pending.page, pending.disk_read) } else { /* cache check, disk read, insert into pending_reads */ };
    (pending checked before the cache) and the only removal is `self.pending_reads.write().remove(&page_idx)` on the `Done` path.
    `reset_internal_states()` at e414a54 (pager.rs:5295) resets checkpoint/commit/allocate/free/spill/vacuum/header states but has no `pending_reads` line; `rollback()` (pager.rs:5262) calls `clear_page_cache` + `reset_internal_states` — the map survives rollback.
    The fixer's own description (4b025575) confirms the failure class: "An abandoned CREATE INDEX can roll back page-cache contents while resumable pager state still points at pre-rollback PageRefs… allocate a page that has already become a btree page, triggering the freelist leaf overflow-cell panic (#7684)", and its diff adds `self.pending_reads.write().clear();` to `reset_internal_states` plus a `reset_internal_states()` call at the start of `rollback_to_snapshot` (savepoint rollback previously had no reset at all).

## [A19-2] `invalidate_btree_cache` clears the page stack without unpinning: pinned-page leak → `CacheError(Pinned)` failures
- commit: f63bd46fa2a9329b538076fd72603c883f173c78 "Merge 'core/storage: port SQLite's saveAllCursors to a pager-level registry' from Jussi Saurio" (2026-06-04)
- file: core/storage/btree.rs:6327 (at fixer commit; the buggy body was btree.rs ~6302 at f63bd46)
- at-head: fixed-by 496c24ed85d2a7cf4963f12537e3c539144765a7 (2026-06-22, "core/btree: prevent leaking pinned pages in page stack")
- category: error-handling
- severity: medium
- confidence: high
- description: The saveAllCursors port extended `invalidate_btree_cache` to drop the cursor's page stack, but did it by writing `*slot = None` over each stack slot and setting `current_page = -1`. Stack slots hold pages pinned via the pin counter (`PageStack::clear()` exists precisely to `unpin_all_and_clear_slots`); overwriting the slot drops the `Arc` without decrementing `pin_count`, so the pages remain pinned in the shared page cache forever. Pinned pages cannot be evicted, so under cache pressure the pager eventually cannot make room and operations fail.
- failure: A statement holds a peer cursor on a btree; another cursor's `clear_btree`/rollback path invokes `invalidate_btree_cache` on the peer (the exact new call sites this commit added: `Pager::invalidate_peer_cursors`, `Pager::invalidate_all_cursors` on rollback). Each invalidation leaks the pins of every page on that cursor's stack. In a write-heavy workload with spilling, the cache fills with unevictable pinned pages and a later operation fails with `CacheError(Pinned { pgno: N })` — reproduced deterministically by the simulator seed in the fix PR (`--profile write_heavy_spill --seed 9227228821763364487`).
- evidence: |
    f63bd46 added (core/storage/btree.rs):
        fn invalidate_btree_cache(&mut self) {
            for slot in self.stack.stack.iter_mut() { *slot = None; }
            self.stack.current_page = -1;
            self.has_record = false; ...
    496c24e replaces exactly those three lines with `self.stack.clear();` whose impl (HEAD btree.rs:8398) is `self.unpin_all_and_clear_slots(); self.current_page = -1;`. The fixer's commit message: "This is due to `invalidate_btree_cache` not unpinning the pages when clearing the page stack" and cites the `CacheError(Pinned { pgno: 29 })` simulator failure.

## [A19-3] `pending_peer_save` holds raw cursor pointers across IO yields: use-after-free if a peer statement is reset/dropped mid-yield
- commit: f63bd46fa2a9329b538076fd72603c883f173c78 "Merge 'core/storage: port SQLite's saveAllCursors to a pager-level registry' from Jussi Saurio" (2026-06-04)
- file: core/storage/btree.rs:6081-6111 (`drive_pending_peer_save` at HEAD), core/storage/pager.rs:1690+ (`RegisteredCursor`)
- at-head: present
- category: memory
- severity: high
- confidence: medium
- description: The cursor registry stores raw `NonNull<dyn CursorTrait>` pointers (`RegisteredCursor`); its safety argument is that a connection runs one statement at a time so no aliasing access occurs. But `drive_pending_peer_save` (run at the head of every `insert()`/`delete()`) snapshots those raw pointers into `self.pending_peer_save` and then iterates with IO yields in between: `try_save_position_for_external_balance` on an index peer calls `record()`, which can yield reading an overflow-chain page (or on cache spill). While the writing statement is parked on that yield, the application can legally reset or drop the *peer's* statement; `ProgramState::reset` drops all cursors (`self.cursors.iter_mut().for_each(|c| { c.take(); })`, core/vdbe/mod.rs:1017), which frees the `Box<BTreeCursor>` and removes it from the registry — but the writer's `pending_peer_save` snapshot is not scrubbed (unregister_cursor, pager.rs:1720, only edits the registry bucket). On resume, `peer.as_mut()` dereferences freed memory.
- failure: One connection, two prepared statements: R = `SELECT * FROM t WHERE k > ... ORDER BY k` using index `i1` and currently positioned on a row whose index key spills to an overflow page (k is a multi-KB TEXT); W = `DELETE FROM t WHERE ...` (opens a write cursor on `i1`). App steps W → `delete()` → `drive_pending_peer_save` snapshots `[&R's i1 cursor]`, calls `try_save_position_for_external_balance` → `record()` → overflow page read → step returns IO with `pending_peer_save = Some((ptrs, 0))`. App resets or finalizes R (normal API usage, e.g. GC in a binding) → R's cursor Box freed. App steps W again → `unsafe { peer.as_mut().note_external_row_write(...) }` / `try_save_position_for_external_balance()` executes on the freed allocation → undefined behavior: crash, or silent heap corruption that can propagate into written pages.
- evidence: |
    HEAD core/storage/btree.rs:6094-6110:
        let Some((peers, idx)) = self.pending_peer_save.as_mut() else { ... };
        while *idx < peers.len() {
            let peer = peers[*idx];
            unsafe { peer.as_mut().note_external_row_write(written_rowid) };
            let outcome = unsafe { return_if_io!(peer.as_mut().try_save_position_for_external_balance()) };
            ...
    `return_if_io!` exits the function with the raw pointers parked in `self.pending_peer_save` (btree.rs:871). `try_save_position_for_external_balance` yields via `record()` for index cursors (btree.rs: "Index btree: yield IO for overflow chains"). Nothing invalidates other cursors' `pending_peer_save` on cursor drop/unregister; grep shows the only writes to `pending_peer_save` are in `drive_pending_peer_save` itself and the field initializer. The type-level SAFETY comment (pager.rs) only covers aliasing ("no other reference to the referent cursor is live"), not lifetime — the referent can be freed while the snapshot is parked across a yield.

## [A19-4] Debug `eprintln!` probes with hard-coded page ids shipped in WAL hot paths

- file: core/storage/wal.rs (find_frame ~line 906, prepare_frames ~4100, append_frames_vectored ~4285 at the commit)
- at-head: fixed-by ed5032f6723a3123e9492c958f6e01c9fa8d8351 (2026-07-06, "remove debug code")
- category: other
- severity: low
- confidence: high
- description: The spill-frame-reuse fix accidentally merged its investigation instrumentation: `[WHOPPER_*_PROBE]` `eprintln!` calls guarded by hard-coded values (`page_id == 12075 || page_id == 11505 || frame_id == 5161`), plus an unconditional probe in `prepare_frames` whenever the local snapshot is ahead of the authority (which is every spill/raw-frame commit). `find_frame` is on the per-page-read hot path; for any real database large enough to contain page 12075 (≈47 MB at 4 KB pages), every read of that page locked the WAL-header spinlock, cloned the page's frame list, and printed a multi-line state dump to stderr.

## Batch summary
- reviewed: 20 commits (0 skipped entirely; d01d16d's only in-scope hunk was an MVCC-gating validation change in `journal_mode.rs::open_mv_store`, experimental-path-only, no stable-path effect; f321fff, 3de4d58, 61b0877, 1144f2c, 6961e45, a01b247, ed5032f are test-only/logging/annotation changes)
- notable-but-not-findings / hunches:
  - Suspended-mid-operation cursors defeat the saveAllCursors port (f63bd46): the peer-save/restore runs only at operation *entry points* (insert/delete heads; restore in next/prev/rowid/record). A cursor parked mid-`next()` (advance_state=Advance, or `iteration_pending_descent=Some(page)`) that gets saved/invalidated by a peer write resumes its in-flight descent against a page number the peer's balance may have freed/rewritten → wrong rows or Corrupt error. Requires two interleaved statements on one connection with one suspended inside a btree op; exposure predates the batch (before f63bd46 there was no protection at all), so not filed as an introduced bug — but verifiers looking at interleaved-statement corruption should start here.
  - `restore_context`'s NotFound branch (f63bd46) unconditionally re-seeks `GE{eq_only}` and sets `skip_advance=true`, mirroring SQLite's CURSOR_SKIPNEXT — but only `next()` consumes/clears the flag; `prev()` neither consumes nor clears it (SQLite's btreePrevious clears skipNext and handles the sign). After a peer deletes the row under a backwards-iterating cursor, `prev()` still returns the right row, but the stale `skip_advance=true` survives until the next `seek/rewind/next` — a later `next()` on that cursor without an intervening re-seek would return the current row instead of advancing (duplicate row). Could not construct a real plan doing prev-then-next without a re-seek; parked as a hunch.
  - The `read_page` cache-hit torn-read race (locked-but-unloaded page returned with `None` completion) fixed by 6ec5643 predates this batch (the unguarded cache-hit path exists in the pre-image of e414a54); e414a54 carried it forward rather than introducing it.
  - f321fff disables `test_shutdown_checkpoint_truncates_after_restart` on Windows with reason "shutdown checkpoint does not truncate the WAL file to zero on Windows" — an acknowledged platform durability/behavior gap tracked in separate issues, left unfixed.
  - 5d94115 replaces two tolerant recovery paths with `turso_assert` panics (`prepare_frames`: local max_frame must equal authority max_frame when not ahead; `rollback`: savepoint position must be same WAL generation and ≥ committed mark). The invariants hold for all in-tree paths (all write upgrades go through `Pager::begin_write_tx` → `materialize_savepoint_wal_positions`), but any future path that publishes committed frames while a savepoint is open (e.g. raw-frame `wal_insert_frame` commits inside an open savepoint) would panic in production instead of clamping like SQLite.
  - efabb24's new `WalFile::dirty` flag is per-connection state documented as a property of "the WAL file"; today it only ever *skips* an fsync when the committing connection itself appended nothing since its last successful fsync (safe), but the naming invites future misuse as a cross-connection durability signal.
  - e414a54 dropped the `turso_assert!(...loaded...)` "Unable to read WAL shared state" check when converting `open_shared_if_exists` to the non-blocking driver (the loaded flag is now set inside the driver's finalize paths); no scenario found where recovery completes without it, noted for completeness.
