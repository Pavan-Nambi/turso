# Batch A16 findings

## [A16-1] to_sql() drops DESC and COLLATE from table-level UNIQUE constraints, corrupting the autoindex after ALTER TABLE + reopen
- commit: e4785093cd97d5ca381ec9b446b45e04bd687ab6 "Merge 'core/schema: Emit table-level UNIQUE constraints in BTreeTable::to_sql()' from Jussi Saurio" (2026-02-26)
- file: core/schema.rs:3763-3786 (emission loop; `sql.push_str(", UNIQUE (")` at 3778)
- at-head: present
- category: data-corruption
- severity: critical
- confidence: high
- description: The commit made `BTreeTable::to_sql()` emit table-level UNIQUE constraints (fixing a reopen panic), but it emits only the column names. The parsed `UniqueSet` carries each column's sort order (and, since a later commit, collation), and schema load builds the automatic index from those attributes (`core/schema.rs:1884-1902` uses `unique_column.sort_order`). Any ALTER TABLE that rewrites the stored SQL through `to_sql()` (ADD/DROP/RENAME COLUMN) silently turns `UNIQUE(a DESC, b)` into `UNIQUE (a, b)` and `UNIQUE(a COLLATE NOCASE, b)` into `UNIQUE (a, b)`. After reopen, the in-memory index claims ASC/BINARY while the on-disk autoindex b-tree entries were written in DESC/NOCASE order, so index seeks binary-search with the wrong ordering: uniqueness checks miss existing keys, duplicates get accepted, and equality lookups silently return the wrong rows.
- failure: Reproduced against the HEAD build:
    1. `CREATE TABLE t(a INTEGER, b TEXT, UNIQUE(a DESC, b)); INSERT INTO t VALUES (1,'x'),(2,'y'),(3,'z'); ALTER TABLE t ADD COLUMN c INT;` — stored SQL becomes `CREATE TABLE t (a INTEGER, b TEXT, c INT, UNIQUE (a, b))` (DESC gone).
    2. Reopen the database; `INSERT INTO t(a,b) VALUES (1,'x');` — succeeds even though (1,'x') already exists (UNIQUE violated).
    3. `SELECT * FROM t WHERE a=1 AND b='x';` returns only one row although two exist (silent wrong results).
    4. `PRAGMA integrity_check;` reports "row 1 missing from index sqlite_autoindex_t_1", "non-unique entry in index sqlite_autoindex_t_1".
    Same corruption reproduced with `UNIQUE(a COLLATE NOCASE, b)`: after ALTER+reopen, `INSERT ('ABC', '1')` next to existing `('abc','1')` is accepted and integrity_check fails.
- evidence: |
    core/schema.rs:3778-3785 (HEAD):
        sql.push_str(", UNIQUE (");
        for (i, unique_column) in unique_set.columns.iter().enumerate() {
            ...
            sql.push_str(&quote_ident(&unique_column.name));   // sort_order and collation of UniqueSetColumn never emitted
        }
    core/schema.rs:1891-1892 (schema load builds the index from the parsed constraint):
        column_indices_and_sort_orders.push_within_capacity((pos_in_table, unique_column.sort_order))
    Repro transcript above (run with target/debug/tursodb at HEAD 5f6098a0): duplicate accepted + "row ... missing from index" from PRAGMA integrity_check.
    Note: before this commit the same scenario panicked on reopen (orphaned autoindex); the commit replaced a loud crash with silent corruption for DESC/COLLATE unique sets, which violates the project's "crash > corrupt" rule. Collation loss became reachable when UniqueSetColumn later gained a `collation` field, but the emitter introduced here was never updated.

## [A16-2] Preserving column-name case broke NATURAL JOIN / USING column matching (valid queries errored for ~3 months)
- commit: e66ad33f8b0e7afd02dbde905533ce48df3116c7 "Merge 'return columns with correct casing' from Mikaël Francoeur" (2026-03-11)
- file: core/schema.rs:4877-4878 (`Column::new(Some(name), ...)` stores the un-lowercased name); breakage manifested in `parse_join` in core/translate/planner.rs
- at-head: fixed-by 676b3d95b5143e29d5ae85a1939d250226a30796 ("core/translate: case-insensitive NATURAL JOIN and USING column lookup", 2026-06-05)
- category: sql-semantics
- severity: high
- confidence: high
- description: Before this commit every `Column::name` was normalized to lowercase at creation, so scattered exact-match (`==`) comparisons against normalized needles were correct. The commit switched storage to preserve original casing and updated comparisons in core/schema.rs and one spot in update.rs to `eq_ignore_ascii_case`, but missed the NATURAL JOIN common-column discovery and USING-clause expansion in `parse_join`, which still compared the join column name against `Column::name` with `==`. Any shared column that is not all-lowercase stopped matching.
- failure: `CREATE TABLE a("MyCol" INT, x INT); CREATE TABLE b("MyCol" INT, y INT); SELECT * FROM a JOIN b USING (MyCol);` (or `NATURAL JOIN`) fails with "cannot join using column MyCol - column not present in both tables" on every build merged between 2026-03-11 and 2026-06-05, although the query is valid and works in SQLite.
- evidence: |
    The fix commit's own message documents the causal chain: "`Column::name` preserves the original casing ... so any column that wasn't already all-lowercase failed the lookup with 'cannot join using column <name> - column not present in both tables'. Switch all three comparison sites ... to `eq_ignore_ascii_case`" (676b3d95, fixes #7371).
    Case preservation was introduced exactly here: the diff replaced `Column::new(Some(normalize_ident(&name)), ...)` with `Column::new(Some(name), ...)` (core/schema.rs hunk in e66ad33f) without auditing planner.rs, whose `==` comparisons only worked because of the old lowercase invariant.

## [A16-3] Locale collation ids stored in a 12-bit field but registry allows 65k ids — silent collation truncation via `& COLL_MASK`
- commit: d89434d889f96374f396dd4c0eaf3739b398bf46 "Merge 'Add locale-backed collations to Turso' from Aziz Batihk" (2026-05-20)
- file: core/schema.rs:5339 and 5407 (masked stores); core/translate/collate.rs:232-247 (LocaleCollationId::from_index cap)
- at-head: present
- category: logic
- severity: medium
- confidence: high
- description: Column collation is packed into 12 bits of `Column.raw` (`COLL_MASK = 0b1111_1111_1111 << COLL_SHIFT`), storing `CollationSeq::to_bits()` which for locale collations is `registry_index + 4` and can be up to `u16::MAX` (`LocaleCollationId::from_index` only rejects indexes above `u16::MAX - 4`). Both store sites mask with `& COLL_MASK`, silently discarding high bits instead of failing. The registry is a process-global, append-only Vec keyed by name, so after 4092 distinct locale collations have been registered in a process, the next one has `to_bits() = 4096`, which masks to 0 (= Unset, read back as Binary); later ids wrap to NoCase/Rtrim/other locales.
- failure: A long-running process (multi-tenant server) that has seen 4092 distinct locale collation names: `CREATE TABLE t(a TEXT COLLATE "sr-Latn-RS")` (the 4093rd distinct locale) — the column's stored collation bits become 0, `collation()` reads Binary, so comparisons, ORDER BY, and any UNIQUE index on the column use BINARY instead of the declared locale, with no error. The 4094th wraps to NoCase, i.e. an entirely different collation than declared. If such a column backs an index, entries are inserted in the wrong order relative to the declared collation and a later process (with a fresh, smaller registry) reads the schema with the correct locale id → same seek-order corruption class as A16-1.
- evidence: |
    core/schema.rs:5241: `const COLL_MASK: u32 = 0b1111_1111_1111 << COLL_SHIFT;` (12 bits)
    core/schema.rs:5339: `raw |= (u32::from(c.to_bits()) << COLL_SHIFT) & COLL_MASK;` (silent truncation, same at 5407)
    core/translate/collate.rs:233: `if index > (u16::MAX - Self::FIRST_STORAGE_BIT) as usize { return Err(... "too many locale collation sequences" ...) }` — cap is 65531, not 4091, so the error that should fire at the 12-bit boundary never does.
    from_storage_bits(0) → Unset → `Column::collation()` maps Unset to Binary (core/schema.rs:5389-5394), so nothing detects the mismatch.

## [A16-4] generate_series with a literal NULL stop scans 4,294,967,295 rows instead of returning an empty result
- commit: d3c593a10e5ba54367d15b3347d46dc31c3c7066 "Merge 'fix: default `generate_series` STOP to SQLite Default (4294967295) when omitted' from Damian Melia" (2026-02-20)
- file: core/series.rs:171,183-185
- at-head: present
- category: perf-regression
- severity: medium
- confidence: high
- description: The commit makes `filter()` default `stop` to 4294967295 whenever the planner did not push a stop constraint (`idx_num & 2 == 0`). But the planner drops constraints that compare against a literal NULL (it emits a `NotNull` post-filter on the hidden `stop` column instead of passing the arg to VFilter), so `generate_series(1, NULL)` now instantiates the full 1..4294967295 series and post-filters every row (all rejected). Before this commit the omitted-stop path left `stop = -1`, hit the `stop == -1 → EOF` branch, and returned 0 rows instantly — accidentally matching SQLite, whose series.c returns no rows when any passed constraint is NULL. The later sentinel fix (de101284) kept this behavior: only a stop argument that actually reaches `filter()` as NULL yields EOF.
- failure: `SELECT * FROM generate_series(1, NULL);` — SQLite: 0 rows instantly. Turso at HEAD: iterates ~4.29 billion rows before returning 0 rows; a debug build did not finish within a 15s timeout (verified; EXPLAIN shows VFilter receiving only the start argument plus a `VColumn(stop)`/`NotNull` post-filter loop). Realistic trigger: any SQL generator or macro that inlines a NULL literal for the stop bound; the query appears hung for minutes even in release builds.
- evidence: |
    core/series.rs:180-185 (HEAD):
        if idx_num & 2 != 0 { stop = extract_arg_integer!(args, arg_idx); ... }
        else { stop = DEFAULT_STOP_OMITTED; }   // Some(4294967295) — also taken when the planner dropped a NULL literal
    EXPLAIN output at HEAD for `SELECT * FROM generate_series(1,NULL)`:
        3  VFilter 0 9 1        (only 1 arg: the start)
        4  VColumn 0 2 4        (reads hidden stop column)
        5  NotNull 4 8          (post-filter rejects every row)
        8  VNext   0 4          (loops over the whole 4.29B-row series)
    Runtime check: `SELECT * FROM generate_series(1,(SELECT 5 WHERE 0))` (NULL arrives as a runtime arg) returns 0 rows instantly via the `stop.is_none() → EOF` branch, confirming the divergence is specific to the planner-dropped literal-NULL case introduced by the new default.

## Batch summary
- reviewed: 20 commits (0 skipped as excluded-only; 4 were trivial fallible-allocation/formatting refactors)
- notable-but-not-findings / hunches:
  - `BTreeTable::to_sql()` has more lossy/unsafe emission paths that predate this batch (introduced 2026-02-16, commit 515b1a70, outside this batch): table-level `PRIMARY KEY (...)` and `FOREIGN KEY (...)` push raw, unquoted column names (core/schema.rs:3699, 3706-3719) and drop PK sort order (`PRIMARY KEY(a DESC)`) — same ALTER+reopen corruption class as A16-1. Whoever owns that batch should check it.
  - Case-preservation follow-ups: `Index::from_sql` still stores normalized (lowercased) index column names while table columns keep original case; every cross-comparison must be case-insensitive. Later commit 112eb468 "Match SQLite ASCII-only case folding for object names" suggests stragglers kept surfacing after e66ad33f.
  - generate_series pre-existing divergences (both sides of the batch commits, not introduced by them): `generate_series(NULL, 5)` raises "Extension error: Invalid Argument" where SQLite returns 0 rows; NULL step is treated as 1 instead of producing 0 rows.
  - Locale collation registry (d89434d8) is process-global and append-only: distinct collation names are never evicted (unbounded growth), and ICU-version-dependent sort orders are baked into on-disk index ordering — cross-version/platform reopen could mis-order persisted indexes (design-level risk, no concrete repro).
  - `SELECT count(*) FROM generate_series(1)` legitimately enumerates 4.29B rows (SQLite-compatible after d3c593a1) — debug-build tests using unbounded single-arg series will appear to hang.
  - 861b6d2a (ALTER for virtual columns) `shift_generated_column_indices_after_drop` early-returns when `has_virtual_columns` is false; safe today only because STORED generated columns are rejected at parse ("Stored generated columns are not supported") — if STORED support lands, dropped-column index shifting silently skips them.
