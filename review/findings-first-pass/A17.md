# Batch A17 findings

## [A17-1] Named savepoints capture their WAL rollback position without any lock; ROLLBACK TO installs a stale/dead-generation position, corrupting WAL state and reader visibility
- commit: 2706498e767f98ca30f17705f4b7f0b93c4ad474 "Merge 'Implement named savepoints' from Preston Thorpe" (2026-02-19)
- file: core/storage/pager.rs:1869 (at commit, `open_savepoint_with_kind` capturing `wal.get_max_frame()`); rollback consumer core/storage/wal.rs:1709 (at commit, `frame_cache.retain`); fixed code now at core/storage/pager.rs:3034 (`materialize_savepoint_wal_positions`)
- at-head: fixed-by 46cd926d34989b13dd68efcbab2fe4f8b6fc2208 (2026-07-07; earlier partial mitigation b8ae9ccf0ad9735f1d7dd5ed88f923214aca497f, 2026-05-07)
- category: data-corruption
- severity: critical
- confidence: high
- description: `SAVEPOINT name` records the WAL rewind target (`wal_max_frame`, checksum) at savepoint-open time via `wal.get_max_frame()`. Unlike the pre-existing statement savepoints (opened in `OpTransactionState::BeginStatement`, i.e. after the write-lock upgrade), the new `op_savepoint` Begin path takes no read or write transaction at all, so it snapshots the connection's *private* `max_frame`, which can be stale (another connection committed since) or belong to a WAL generation that is destroyed when this connection's later write upgrade restarts the log (`try_restart_log_before_write`). `ROLLBACK TO` then feeds that position into `Wal::rollback(Some(RollbackTo{..}))`, which (a) stores it as the connection's `max_frame`/`last_checksum` and (b) prunes the *shared* `frame_cache` down to that frame — purging frames committed by other connections, or keeping this connection's own rolled-back frames visible.
- failure: Single connection, WAL fully backfilled (e.g. after `PRAGMA wal_checkpoint(TRUNCATE)` left private max_frame = M0 > 0): `SAVEPOINT sp;` (captures M0 from the old generation) → `INSERT INTO t VALUES(1);` (write upgrade restarts the log; the INSERT appends frame 1 of the new generation) → `ROLLBACK TO sp;` installs frame M0 + old checksum: the rolled-back frame 1 stays ≤ M0 so it remains visible in the frame cache (SELECT still returns the "rolled back" row), and the next append continues at M0+1, leaving a gap of stale bytes; on reopen, WAL recovery fails salt/checksum validation at the gap and committed data after it is lost (integrity_check errors). Multi-connection variant: conn A's private max_frame is behind shared committed max (conn B committed since A's last read); `SAVEPOINT sp; INSERT ...; ROLLBACK TO sp;` on A prunes B's committed frames out of the shared `frame_cache`, so all connections silently read pre-B page images from the DB file — wrong query results.
- evidence: |
    At the commit, core/storage/pager.rs:1856-1875 (`open_savepoint_with_kind`) runs with no lock:
        let (wal_max_frame, wal_checksum) = if let Some(wal) = &self.wal {
            (wal.get_max_frame(), wal.get_last_checksum())
        } else { (0, (0, 0)) };
    and op_savepoint Begin (core/vdbe/execute.rs:2637+) does only `pager.open_subjournal()` + `pager.with_header(...)` + `open_named_savepoint(...)` — no `begin_read_tx`/`begin_write_tx`. `Wal::rollback` (core/storage/wal.rs:1691-1717 at commit) applies the stale target to shared state:
        frame_cache.retain(|_page_id, frames| { while frames.last().is_some_and(|&f| f > max_frame) { frames.pop(); } ... });
        self.max_frame.store(max_frame, Ordering::Release);
    Both fixers state the defect directly. b8ae9ccf: "Savepoints can be opened on a stale connection-local WAL snapshot. Do not let that rollback remove frame-cache mappings for frames that are already globally committed by another connection." 46cd926d: "Savepoints captured their WAL rollback position when opened, possibly under only a read transaction. If the WAL was then restarted at the write upgrade ... ROLLBACK TO installed a position from the dead generation: the next append continued at a bogus offset, rolled-back frames stayed visible to readers, and the commit's frames failed salt/checksum validation during recovery (integrity_check errors, lost committed data)." HEAD instead stamps positions in `Pager::begin_write_tx` → `materialize_savepoint_wal_positions()` (core/storage/pager.rs:3026-3050) and asserts generation/high-water-mark in `rollback` (core/storage/wal.rs:4086+).

## [A17-2] Savepoint operations permitted while a write statement is suspended mid-execution; ROLLBACK TO restores pages underneath the suspended writer, which then resumes over inconsistent page state
- commit: 2706498e767f98ca30f17705f4b7f0b93c4ad474 "Merge 'Implement named savepoints' from Preston Thorpe" (2026-02-19)
- file: core/vdbe/execute.rs:2637 (at commit, `op_savepoint` — no active-writer guard); guard now at core/vdbe/execute.rs:4786
- at-head: fixed-by 59d03e62186913c90642dd263a92b3ef2b477100 (2026-07-09)
- category: data-corruption
- severity: high
- confidence: high
- description: SQLite rejects SAVEPOINT/RELEASE with SQLITE_BUSY while other statements are in progress, and permits ROLLBACK TO only because it "trips" all open cursors so affected statements abort instead of resuming. The named-savepoints implementation added SQL-reachable `op_savepoint` with no such guard and Turso has no cursor-tripping. `pager.rollback_to_named_savepoint` replays subjournal page images into the page cache and rewinds the WAL while a suspended write statement still holds a BTreeCursor whose stack, balance state, and cell offsets describe the pre-rollback page contents. When that statement resumes stepping, it writes b-tree structures based on stale offsets into restored pages.
- failure: `BEGIN; SAVEPOINT sp;` then `stmt = prepare("INSERT INTO t SELECT ... RETURNING id"); stmt.step()` → returns first Row, leaving the b-tree write in flight; on the same connection execute `ROLLBACK TO sp;` (succeeds — no guard, restores page images / rewinds WAL); `stmt.step()` resumes the insert/balance over the rolled-back pages → corrupt b-tree (bad cell pointers / lost rows) or an internal assertion crash. Same interleaving is reachable with any statement suspended at an I/O yield instead of RETURNING.
- evidence: |
    At the commit, `op_savepoint` (core/vdbe/execute.rs:2637-2737) dispatches Begin/Release/RollbackTo straight into pager mutation with no check of in-flight statements; `rollback_to_named_savepoint` (core/storage/pager.rs:1818+) replays the subjournal into the live page cache unconditionally. The fixer 59d03e62 states: "Turso had no such guard: a savepoint could be opened at a mid-statement I/O boundary of a suspended writer, and ROLLBACK TO could restore pages underneath it, letting the writer resume over a mix of rolled-back and in-flight page states." HEAD now returns `LimboError::StatementsInProgress` for all three ops when `conn.n_active_writes > 0` (core/vdbe/execute.rs:4786-4792).

- notable-but-not-findings / hunches:
  - 0936aca8 (WAL read lock on rollback): the new `op_checkpoint` hunk (`core/vdbe/execute.rs:610-620` at HEAD) calls `pager.end_read_tx()` for RESTART/TRUNCATE in autocommit; this drops the *connection-wide* single read slot that another in-flight statement (e.g. half-stepped SELECT) of the same connection may be relying on, and then truncates/restarts the WAL under it. Not filed as a finding because the halt path already does the same (`commit_txn_wal` → `TransactionState::Read` arm calls `pager.end_read_tx()` when any interleaved autocommit statement finishes), i.e. Turso's one-read-slot-per-connection model makes interleaved statements unsafe regardless of this commit. Systemic issue worth a dedicated look.
  - 2706498e silently reverted 0936aca8's read-lock release in `WalFile::reset_internal_states` the same day it merged (likely a merge-conflict resolution). Verified benign because `Pager::rollback_tx` ends with `wal.end_read_tx()` (proper unlock) and `rollback()` no longer clobbers `max_frame_read_lock_index`, but it is a canonical example of a same-day merge undoing a fix.
  - halt() deferred-FK failure path (touched by dd21e046, but behavior pre-existing) rolls back the entire transaction and flips auto_commit=true; SQLite instead fails the COMMIT and leaves the transaction active. Divergence predates this batch.
  - `subjournal_page_if_required` (core/storage/pager.rs:1898) consults only the newest savepoint's page bitmap, unlike SQLite's subjRequiresPage which checks every open savepoint. Reasoned through several nestings (release merges child journal ranges into the parent; replay is first-image-wins over a contiguous range) without finding a wrong-restore interleaving, but the invariant is subtle and worth an adversarial pass.
  - b3138e53 (skiplist TursoAllocator + fallible inserts): allocator-failure path checked for counter leaks/UB (len fetch_add correctly moved after `try_alloc`); consumer is MVCC-only, so any residual issue is confined to the excluded area.
