## [A10-1] repeat()/lpad()/rpad() allocate attacker-controlled length with no limit -> process abort/OOM from plain SQL
- commit: c681ded595246a072f7aa631df2a6ca983eea3a6 "Merge 'Add SQL-standard scalar functions and PG-compatible aliases' from Glauber Costa" (2026-06-17)
- file: /home/user/turso/core/functions/string.rs:31 (repeat), :70-95 (pad)
- at-head: present
- category: error-handling
- severity: high
- confidence: high
- description: The new `exec_repeat` calls `s.repeat(n as usize)` with `n` taken straight from the SQL argument (i64, or a float saturated via `f as i64`, so up to i64::MAX). There is no cap: the project's own norm is `Value::MAX_BLOB_LENGTH` (1 GB) + `LimboError::TooBig` + fallible `try_vec!` (see `exec_randomblob`/`exec_zeroblob` in core/vdbe/value.rs:309-330). `str::repeat` uses the infallible global allocator, so a huge count either aborts via `handle_alloc_error` (not a catchable error) or commits gigantic memory and gets OOM-killed. `pad()` has the same defect: `target_len` is unbounded and `fill_chars.iter().cycle().take(target_len - char_count).collect::<String>()` builds a string of up to i64::MAX characters. No later commit touched core/functions/string.rs, so this is live at HEAD.
- failure: `SELECT repeat('ab', 9223372036854775807);` or `SELECT lpad('x', 200000000000);` -> attempted multi-hundred-GB allocation -> `memory allocation of N bytes failed` abort (or OOM kill) of the whole process embedding turso_core, instead of a catchable "too big" SQL error. Any application exposing these functions over user-influenced counts is a one-statement DoS; for an embedded production DB a process abort can also interrupt in-flight transactions.
- evidence: |
    core/functions/string.rs:27-31 (HEAD):
        if n <= 0 {
            return Value::build_text(String::new());
        }
        Value::build_text(s.repeat(n as usize))
    core/functions/string.rs:70,86-95 (HEAD): `let target_len = target_len as usize;` then
        let pad: String = fill_chars.iter().cycle().take(target_len - char_count).collect();
    Contrast with the project norm in core/vdbe/value.rs:318-327:
        if length > Self::MAX_BLOB_LENGTH { return Err(LimboError::TooBig); }
        let mut blob = crate::alloc::try_vec![0; length as usize]?;
    Count coercion in exec_repeat also saturates floats (`f as i64`), so `repeat('a', 1e30)` hits the same path.

## [A10-2] gcd()/lcm() panic on (i64::MIN, -1) via `i64::MIN % -1` remainder overflow
- commit: c681ded595246a072f7aa631df2a6ca983eea3a6 "Merge 'Add SQL-standard scalar functions and PG-compatible aliases' from Glauber Costa" (2026-06-17)
- file: /home/user/turso/core/functions/math.rs:28-32 (guard now present at :23-25)
- at-head: fixed-by e08485d6 (merged in b3a2956290fff8d1b27a43e00394a7e39a847f59, 2026-07-28)
- category: logic
- severity: medium
- confidence: high
- description: `gcd_inner` special-cased `a == i64::MIN || b == i64::MIN` but only bailed for `a==0 || b==0 || a==b`, then did `a %= b` (or `b %= a`). For the pair (i64::MIN, -1) that evaluates `i64::MIN % -1`, which rustc guards unconditionally: it panics "attempt to calculate the remainder with overflow" even in release builds (verified with `rustc -O`). The mathematically correct answer is 1. `exec_lcm` calls `gcd_inner` first, so lcm hit the same panic. Live from 2026-06-17 until the "Fix panics" merge on 2026-07-28 added the `-1` guard plus tests.
- failure: `SELECT gcd(-9223372036854775808, -1);` (or `lcm(-9223372036854775808, -1)`, or either argument order) -> runtime panic in the VDBE function op -> statement/process crash instead of returning 1 (gcd) / an IntegerOverflow error (lcm).
- evidence: |
    At the introducing commit (git show c681ded:core/functions/math.rs):
        if a == i64::MIN || b == i64::MIN {
            if a == 0 || b == 0 || a == b { return None; }
            if a == i64::MIN { a %= b; } else { b %= a; }   // a=MIN, b=-1 -> MIN % -1 -> panic
        }
    Verified `i64::MIN % -1` panics under `rustc -O` ("attempt to calculate the remainder with overflow", exit 101).
    Fix at HEAD core/functions/math.rs:23-25 adds `if a == -1 || b == -1 { return Some(1); }` with regression tests `gcd_min_by_minus_one` / `lcm_min_by_minus_one` (commit message of the fix: "core/functions: fix gcd/lcm overflow on i64::MIN % -1").

## [A10-3] datetime numeric-string whitespace trim omits vertical tab, diverging from SQLite
- commit: 47032e1e85548d5ef321131372f1e4c234a9342e "Merge 'core/vdbe: Make scalar function edge cases SQLite compatible' from Ben Zaid" (2026-06-08)
- file: /home/user/turso/core/functions/datetime.rs:222
- at-head: present
- category: sql-semantics
- severity: low
- confidence: high
- description: The commit made numeric date/time strings tolerate surrounding whitespace by trimming with Rust's `char::is_ascii_whitespace` (space, \t, \n, \x0C, \r). SQLite's `sqlite3AtoF`/ctype table additionally treats vertical tab \x0B as whitespace, so SQLite parses `'5' || char(11)` as Julian day 5 while Turso still returns NULL. This is the exact bug class the fix was for (the earlier reverted attempt cited a differential-fuzzer INSERT storing NULL where SQLite stored -210865982400), and the fix leaves one whitespace character uncovered. Not a behavior regression relative to pre-commit (all whitespace was rejected before), but an incomplete compatibility fix that is live at HEAD.
- failure: `SELECT unixepoch('5' || char(11));` -> Turso NULL, real SQLite (3.45.1 oracle verified) -> -210866328000. In a differential/replication or INSERT context Turso stores NULL where SQLite stores a number (silent data divergence).
- evidence: |
    core/functions/datetime.rs:222 (HEAD):
        let numeric_value = value.trim_matches(|c: char| c.is_ascii_whitespace());
    Rust `is_ascii_whitespace` = {0x09,0x0A,0x0C,0x0D,0x20}; SQLite's isspace map = {0x09..0x0D,0x20} (includes 0x0B).
    Oracle: `SELECT unixepoch(char(11)||'5'), unixepoch('5'||char(11))` -> (-210866328000, -210866328000) in sqlite3 3.45.1; Turso's trim leaves the 0x0B byte so `parse::<f64>()` fails and every later parser rejects it -> NULL.
