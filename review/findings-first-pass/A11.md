# Batch A11 findings — core/io: io_uring/syscall backends, completions, buffer lifecycle

## [A11-1] `drain_completions` after `cancel()` is a no-op — error paths no longer wait for in-flight kernel I/O
- commit: b1bf20df5f267d36c1a3bedf1af06b4f784a91c9 "Merge 'core/io: improve io_uring IO backend by removing serialization' from Preston Thorpe" (2026-05-11)
- file: /home/user/turso/core/io/mod.rs:460 (drain_completions), /home/user/turso/core/io/completions.rs:460 (abort), call sites /home/user/turso/core/storage/pager.rs:3796-3797 and 4045-4046, /home/user/turso/core/storage/wal.rs:4926-4927, /home/user/turso/core/storage/sqlite3_ondisk.rs:751-752, /home/user/turso/core/vdbe/sorter.rs:428-429
- at-head: present
- category: io
- severity: high
- confidence: high
- description: This commit replaced `IO::drain()` (which, on io_uring, looped `submit_and_wait` + CQ drain until the ring was empty — a true kernel barrier) with `drain_completions(&[Completion])`, which loops `step()` only "while any completion is not finished()". But every error-path call site invokes `io.cancel(...)` (or `group.cancel()`) first, and `cancel` calls `Completion::abort()`, which immediately sets the completion's result (`abort()` → `error(Aborted)` → `result.get_or_init(...)`). So by the time `drain_completions` runs, every listed completion is already `finished()` and the loop exits without processing a single CQE. The documented purpose ("so cancelled ops actually release their buffers before the caller returns") is silently not fulfilled: the function returns while the kernel is still reading/writing the submitted buffers, and the in-flight ops are not even cancelled in the `group.cancel()` paths (CompletionGroup::cancel only aborts, it never submits AsyncCancel). Additionally, a "cancelled" multi-chunk writev whose partial-success CQE arrives later is re-submitted by `handle_writev_completion` and keeps writing its remaining chunks.
- failure: On io_uring, a commit calls `Pager::...` → `append_frames_vectored` in a loop; earlier batches' WAL frame writes are in flight (`state.completions`), then a later batch fails (e.g. allocation/submission error). pager.rs:3796 does `cancel(&state.completions)` + `drain_completions(&state.completions)` — the latter returns instantly — and the transaction errors out without advancing `max_frame`. The next transaction writes different frame bytes at the same WAL file offsets while the earlier (uncancellable, still-in-flight) kernel writes race them. If a stale write lands last, the newly committed frame is clobbered with old content whose checksum does not chain → the later commit's frames are unreadable on recovery/read (silently lost transaction). Same pattern on the checkpoint path (sqlite3_ondisk.rs:751: DB-file writes still landing after `write_pages_vectored` returned an error) and the sorter/btree read paths. Before this commit, `io.drain()` genuinely waited out the ring in all these paths.
- evidence: |
    core/io/mod.rs:460 (HEAD):
        fn drain_completions(&self, completions: &[Completion]) -> Result<()> {
            while completions.iter().any(|c| !c.finished()) { self.step()?; }
    core/io/completions.rs:460 (HEAD):
        pub fn abort(&self) { self.error(CompletionError::Aborted); }   // sets result => finished()==true immediately
    core/io/io_uring.rs:476-488 (HEAD): cancel() calls c.abort() for each completion before submitting AsyncCancel.
    core/storage/pager.rs:3795-3798 (HEAD):
        Err(e) => { self.io.cancel(&state.completions)?; self.io.drain_completions(&state.completions)?; Err(e) }
    Since abort() marks each completion finished, the while-loop condition is false on entry — no step() is ever executed, no CQE drained. The pre-commit code (`git show b1bf20df^:core/io/io_uring.rs`, fn drain) looped `submit_and_wait`+drain until `ring.empty()`. Notably the btree balance path was later rewritten to drain *without* aborting first (core/storage/btree.rs:3415-3422 comments "Drain any in-flight reads ... so the IO scheduler can finalize them"), which only works because that path does not cancel — the cancel-then-drain sites still have the dead barrier.

## [A11-2] `Opening` registry sentinel leaks when an async open is abandoned — later opens of the same path yield forever
- commit: f2908fd4b68cbce9a8b879d68e2ff2c2e426a8e9 "Merge 'core: Drop `DATABASE_MANAGER` lock after lookup' from Pedro Muniz" (2026-04-06)
- file: core/lib.rs (at commit: open_with_flags_async_internal, `registry.insert(key.clone(), RegistryEntry::Opening)` / `state.registry_key = Some(key)`); now /home/user/turso/core/database.rs:462-468
- at-head: fixed-by 6efb903e76c96a442240d0743b0399c6c312a3bd
- category: state-machine
- severity: medium
- confidence: high
- description: The commit replaced holding the DATABASE_MANAGER mutex across the whole async open with an `Opening` sentinel entry inserted at Init and removed on Done (replaced by `Ready`) or on Err. It added no cleanup for the third outcome of an IOResult state machine: the caller stops polling and drops `OpenDbAsyncState` while the open is mid-flight (the classic abandoned-statement case the async-io-model guide warns about). The sentinel then stays in the process-global registry forever. Every subsequent `open_with_flags_async` for that path hits `Some(RegistryEntry::Opening)` and returns `IOResult::IO(Completion::new_yield())`; the sync wrapper `open_with_flags` loops on that yield indefinitely, so the database path becomes permanently unopenable in the process. Fixed nine days later by adding `impl Drop for OpenDbAsyncState` that removes the sentinel (6efb903e, 2026-04-15).
- failure: An async consumer (sync engine or a binding's async open) starts `open_with_flags_async("app.db")`, gets `IOResult::IO` during header/schema load, and the task is cancelled → `OpenDbAsyncState` dropped with `registry_key = Some(File(id))` still set and `Opening` still in DATABASE_MANAGER. Any later `Database::open_file("app.db")` in the same process spins forever: each poll sees `Opening`, yields, retries — an unbounded livelock with no error, until process restart.
- evidence: |
    git diff f2908fd4^ f2908fd4 -- core/lib.rs:
        Some(RegistryEntry::Opening) => {
            // Another caller is already opening this path. Yield so the
            // event loop can make progress and we retry later.
            return Ok(IOResult::IO(types::IOCompletions::Single(io::Completion::new_yield())));
        }
    Cleanup exists only in the Done arm (`state.registry_key.take()` + insert Ready) and the Err arm (`registry.remove`). No Drop impl existed at this commit; `git log -S "impl Drop for OpenDbAsyncState"` shows it first appears in 6efb903e ("add durable snapshot_seq ..."), which removes `registry_key` from the registry on drop (now /home/user/turso/core/database.rs:462-468).

## [A11-3] Registry keyed by OS file identity silently stops de-duplicating databases on IO backends whose paths are not host-filesystem files
- commit: 30d8eaf8a3d789c723c9ccd224c2d47aaf6e7823 "Merge 'core: Switch to file ID for database registry mapping' from Pekka Enberg" (2026-04-01)
- file: /home/user/turso/core/io/mod.rs:513 (default `IO::file_id`), /home/user/turso/core/database.rs:1177 (`if let Ok(file_id) = io.file_id(path)`), /home/user/turso/core/io/vfs.rs (no `file_id` override)
- at-head: present
- category: logic
- severity: medium
- confidence: medium
- description: Before this commit the registry key was `std::fs::canonicalize(path).unwrap_or_else(|| path.to_string())` — registration always happened, for every backend. After it, the key is `io.file_id(path)`, whose default implementation calls `std::fs::metadata(path)` on the host filesystem, and both the lookup and the insert are silently skipped when that fails (`if let Ok(file_id) = io.file_id(path)`). MemoryIO and the test IOs got hash-based overrides, but VFS extension backends (`core/io/vfs.rs`, and any `register_io` backend that doesn't override `file_id`) did not. For a VFS whose paths do not exist on the host FS (e.g. an object-store/network VFS — exactly the use case the later runtime-registrable backend commit advertises with `register_io("s3", ...)`), `file_id` errors on every call, so no database ever enters the registry. The invariant the registry exists for — "there is a single, shared Database object per database file [because] it is not safe to have multiple independent WAL files open" (comment at /home/user/turso/core/database.rs:479-482) — is silently lost for those backends.
- failure: A process registers a custom Rust IO backend "s3" whose paths are virtual, opens `Database::open(io, "bucket/app.db", ...)` twice (two components of one server app). Both opens miss the registry (file_id errors), both create independent `Database` objects with independent `WalFileShared`, page caches, and in-process locks over the same underlying storage. The VFS has no OS-level advisory locks, so both instances can hold the "exclusive" WAL write position simultaneously and append conflicting frames at the same WAL offsets → WAL checksum-chain breakage / lost commits. Before the commit, the second open returned the first instance.
- evidence: |
    core/io/mod.rs:513 (HEAD, default impl):
        fn file_id(&self, path: &str) -> Result<FileId> { get_file_id(path).map_err(...) }   // std::fs::metadata
    core/database.rs:1176-1213 (HEAD): registry lookup AND `state.registry_key = Some(key)` both live inside
        `if let Ok(file_id) = io.file_id(path) { ... }` — on Err there is no sentinel, no registration, no error.
    `grep -rn "fn file_id" core/` shows overrides only in io/memory.rs, io/memory_yield.rs (and a test IO in vdbe/vacuum.rs) — io/vfs.rs has none.
    Pre-commit code (git show 30d8eaf^:core/lib.rs) used canonicalize with a raw-path fallback, so VFS paths were still de-duplicated by string.

## [A11-4] Unix last-process probe now releases the shared lifetime lock before probing, creating a no-lock window that can elect two "last" processes
- commit: 220c0d1666df8c9221cc4dab8ee7d4d57a76ec02 "Merge 'core/windows: fix WAL lock coordination' from Marc-André Moreau" (2026-07-17)
- file: /home/user/turso/core/io/mod.rs:256-270 (`shared_wal_probe_exclusive_while_shared_byte` default), /home/user/turso/core/storage/shared_wal_coordination.rs:1078-1084 (`is_last_process_mapping`)
- at-head: present
- category: concurrency
- severity: low
- confidence: medium
- description: To fix Windows handle-scoped locking, `is_last_process_mapping` was rerouted through a new trait helper that first *unlocks* the caller's shared lifetime lock, then try-locks exclusive, then re-locks shared. The pre-commit Unix code attempted the exclusive lock directly while still holding shared — with fcntl (OFD or POSIX) that is an atomic upgrade attempt, so when the probe failed (other processes alive) the caller never passed through an unlocked state. The new default makes every prober fully release its shared lock for a window even on the failure path. Two processes closing concurrently can interleave so that one probes exclusive during the other's unlocked window, succeeds, and wrongly concludes it is the last mapping holder while the other process still has the coordination file mapped. The experimental multiprocess-WAL feature is opt-in (`enable_multiprocess_wal`), which caps severity.
- failure: Multiprocess WAL enabled; processes P1 and P2 both hold shared lifetime locks and both call `is_last_process_mapping` during shutdown. Interleaving: P2 unlocks shared → P1 unlocks shared → P1 try-exclusive succeeds (no locks held anywhere) → P1 unlocks, relocks shared, returns true; P2's probe then fails and returns false. P1 runs the "last process" shutdown truncate checkpoint and WAL/coordination-file teardown while P2's mapping is still live and P2 is still mid-close — the exact double-authority situation the lifetime lock exists to prevent (e.g. truncating the coordination region while P2 still reads it). The old Unix path could only produce a false "last" if the prober really was alone at probe time.
- evidence: |
    core/io/mod.rs:256-270 (HEAD):
        fn shared_wal_probe_exclusive_while_shared_byte(...) -> Result<bool> {
            self.shared_wal_unlock_byte(offset, kind)?;                  // <-- releases shared before probing
            let probe = match self.shared_wal_probe_exclusive_byte(offset, kind) { ... };
            self.shared_wal_lock_byte(offset, false, kind)?;
            Ok(probe)
        }
    Pre-commit (git show 220c0d16^:core/storage/shared_wal_coordination.rs, is_last_process_mapping):
        shared_wal_try_lock_byte(PROCESS_LIFETIME_LOCK_OFFSET, true, ...)  // attempted while shared still held: atomic
        // unlock + reacquire only on success
    Unix (unix.rs) does not override the new trait default, so the widened window applies to the fcntl backends.

## [A11-6] Windows syscall backend leaks one kernel Event handle per thread; comment wrongly claims the OS reclaims them at thread exit
- commit: 0adb0f66342459f13988ddebcf83dc0ba300c48f "Merge 'core/IO: remove unnecessary Mutex on File IO' from Preston Thorpe" (2026-04-28)
- file: /home/user/turso/core/io/windows.rs:27-58 (IO_EVENT thread_local / with_io_event)
- at-head: present
- category: memory
- severity: low
- confidence: high
- description: The overlapped-I/O rewrite stores a `CreateEventW` handle in a `thread_local! { static IO_EVENT: Cell<HANDLE> }`. `Cell<HANDLE>` has no destructor, so the handle is never `CloseHandle`d when a thread exits; the code comment says it is "closed by the OS on thread exit", but Windows kernel handles belong to the process and are only reclaimed at process exit. Every short-lived thread that performs at least one read/write through WindowsIO permanently leaks one Event object. Secondary issue in the same code: if `WaitForSingleObject`/`GetOverlappedResult` on a pending op ever returns an error path, `pread`/`write_chunk` return `Err` while the kernel still owns the stack-allocated `OVERLAPPED` and the destination buffer — a dangling registration (unlikely to trigger, but it is the documented UB pattern for overlapped I/O).
- failure: A long-running Windows service uses a thread-per-request model (or a shrinking/growing thread pool) with Turso; each new worker thread that touches the database allocates an Event that is never freed. Handle count and kernel object memory grow without bound over days of operation — observable as process handle-count growth in Task Manager and eventual resource exhaustion.
- evidence: |
    core/io/windows.rs:27-35 (HEAD):
        // ... Created lazily on first use and reused for the lifetime of the thread
        // (closed by the OS on thread exit).            <-- incorrect: handles are process-scoped
        thread_local! { static IO_EVENT: Cell<HANDLE> = const { Cell::new(ptr::null_mut()) }; }
    No Drop/destructor exists for the Cell; no CloseHandle call for IO_EVENT anywhere in the file.

## [A11-7] Synchronous waiters busy-spin at 100% CPU while another thread is the io_uring leader
- commit: b1bf20df5f267d36c1a3bedf1af06b4f784a91c9 "Merge 'core/io: improve io_uring IO backend by removing serialization' from Preston Thorpe" (2026-05-11)
- file: /home/user/turso/core/io/io_uring.rs:513-517 (follower try_lock early-return), /home/user/turso/core/io/mod.rs:460-477 (drain_completions / wait_for_completion loops)
- at-head: present
- category: perf-regression
- severity: low
- confidence: high
- description: `step()` now try-locks `wait_lock`; a losing thread returns `Ok(())` immediately on the theory that async callers park on their completion's waker. But the synchronous wait helpers (`IO::wait_for_completion`, `IO::drain_completions`, `Completion::wait`) drive I/O with `while !finished() { self.step()? }`. When another thread is inside `submit_and_wait` as leader, the waiter's `step()` returns instantly and the loop degenerates into a hot spin (no sleep, no park) for the full duration of the leader's kernel wait. Before the commit, the same waiter blocked (slept) on the backend mutex.
- failure: Two connections on different threads over one io_uring `Database`. Thread A is leader inside `submit_and_wait`; thread B commits and reaches `wait_for_completion` on its WAL-write completion. B spins `try_lock-fail → return → loop` continuously, burning a full core until A drains B's CQE — on a loaded box this shows up as unexplained 100% CPU during I/O waits, and in single-shared-core environments (cgroup-limited containers) it actively delays the leader it is waiting on.
- evidence: |
    core/io/io_uring.rs:513-516 (HEAD):
        let Some(_wait_guard) = self.wait_lock.try_lock() else { return Ok(()); };
    core/io/mod.rs:467-470 (HEAD):
        fn wait_for_completion(&self, c: Completion) -> Result<()> {
            while !c.finished() { self.step()? }
    No backoff/park anywhere between the two; pre-commit step() blocked on `self.inner.lock()`.

## Batch summary
- reviewed: 20 commits (3 effectively skipped as trivial/out-of-scope: 97eee942 pastey dep swap; 5b4d18f2 clippy cast removal; b7b5d476 touches only the experimental `win_iocp` backend)
- notable-but-not-findings / hunches:
  - 35085e5a (pwrite/pwritev INT_MAX cap): the Darwin fix caps each *iovec* at `i32::MAX` but Darwin's `writev` fails with EINVAL when the *sum* of iov_len exceeds INT_MAX; two-plus multi-GB buffers in one `pwritev` call would still fail on macOS. Not reachable via the page-sized WAL path (1024 iovecs × page size), only via multi-GB individual buffers. Otherwise the rewritten pwritev loop (buf_to_iovecs/trim_iovecs, EINTR resume) checks out as resumable-correct.
  - b1bf20df: `drain_cq` runs completion callbacks while holding the `RingState` mutex; any callback that submits I/O on the same UringIO would self-deadlock (parking_lot is non-reentrant). Pre-existing pattern (old code held the single inner mutex during callbacks too), preserved by the redesign.
  - 4b3fbcbb (keep_write_buffer_alive): `OnceLock::set(..).expect("write buffer should only be set once")` panics if one Completion is ever passed to `pwrite` twice (retry/resubmit with reused completion). No current caller does; a future retry path would trip it. io_uring's `pwritev` keeps buffers alive via `WritevState.bufs`, so the removed callback captures are all covered today.
  - 66163b3 (MonotonicInstant u128): the epoch is now anchored at the first `now()` call, so `instant - Duration` (the `Sub` impl) underflow-panics during roughly the first `duration` of process lifetime. No production caller currently subtracts a Duration; any new "deadline in the past" arithmetic would panic at startup. `duration_since` truncates u128→u64 nanos (safe for ~584 years).
  - 26eaa8e (windows backend): `File::lock_file` now locks bytes [0, u64::MAX) of the data region; on Windows `LockFileEx` also blocks I/O from *other handles of the same process*, so if any future code path calls `lock_file` on one of two in-process WindowsFile handles for the same file, the other handle's reads/writes start failing with ERROR_LOCK_VIOLATION. Currently no Windows caller.
  - 30d8eaf: the process-wide registry keys only on FileId, not on the IO instance: `lookup_in_registry` uses host-OS `get_file_id`, so opening a path with MemoryIO while a real file of the same path is registered returns the *file-backed* Database to the memory-IO caller. Pre-existing under the path-string scheme, unchanged.
  - da357028 / 8362698b (JSON blob fixes): differentially verified against sqlite3 3.45.1 — malformed-JSONB errors, root-path `json_remove` NULL semantics, `json_valid` blob/JSONB handling, and JSON5 hex ints all match the oracle; no regression found.
