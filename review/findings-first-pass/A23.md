# Batch A23 findings — core/translate

## [A23-1] Row-value IN/NOT IN ignores NULL in non-first tuple components (silent wrong results)
- commit: 98b46b15148723d80a5bffe28b6d234f4ed4abbb "autofix: Row value IN expression crashes with register allocation error" (2026-02-24)
- file: core/translate/expr/condition.rs:71-90 (was core/translate/expr.rs at commit)
- at-head: present
- category: sql-semantics
- severity: high
- confidence: high
- description: The row-value IN comparison path added by this commit reuses the pre-existing scalar `check_null_reg` NULL-tracking mechanism, which only feeds the FIRST register of each tuple into the BitAnd chain (`lhs_reg` and `rhs_reg`). For a row value `(a,b,...)`, the NULL-ness of components 1..n is never tracked. When no exact match is found the code therefore concludes the result is definitively FALSE, even when a non-first component is NULL and the correct three-valued-logic result is NULL (unknown). This silently produces wrong results for both `IN` and `NOT IN` on row values.
- failure: `SELECT (1, NULL) IN ((1, 2))` returns 0 in Turso but NULL in SQLite. `SELECT (1, NULL) NOT IN ((1, 2))` returns 1 in Turso but NULL in SQLite. `SELECT 1 WHERE (1, NULL) NOT IN ((1, 2), (3, 4))` returns a row in Turso but nothing in SQLite. All verified against the python3 sqlite3 oracle with the debug tursodb binary. (When the first component differs, e.g. `(2, NULL) NOT IN ((1,2))`, the result is correct because the first component alone is definitively unequal.)
- evidence: |
    core/translate/expr/condition.rs:71-77 initializes `check_null_reg = BitAnd(lhs_reg, lhs_reg)` — only component 0 of the LHS.
    Lines 85-90: `check_null_reg = BitAnd(check_null_reg, rhs_reg)` — only component 0 of each RHS tuple.
    The row-value comparison (lines 127-183) compares all `lhs_reg+j`/`rhs_reg+j`, but the final NULL decision (lines 186-193: `IsNull check_null_reg -> when_null` else `Goto when_false`) uses only the component-0 null tracking. So a NULL in b/y is invisible to the 3VL decision.
